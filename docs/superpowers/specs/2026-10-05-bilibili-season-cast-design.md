# bilibili 合集投屏：整包识别、本机队列、按序连播与任意选一集

制定日期：2026-10-05 ｜ 状态：**设计已确认，待实现（本文是实现前的 spec，不是变更记录）** ｜ 负责：无常 + AI agent
上游文档：网页地址投屏的实现与红线 `AGENTS.md` §4.14、发送端插件规划书 `docs/Casting-Suite-Plan.md`、

## 0. 这一条要解决什么

用户在手机上看到一集 bilibili 的番剧/合集，复制地址投到 Macast。今天的程序只认**这一条地址
指向的那一集**：解出来、挑一档画质、投出去，然后结束。他要连续看下一集，就得回手机再复制一次。

需求原话：**「识别 bilibili 合集的功能，将合集全部推送，接收端能够按照合集顺序播放，
或者用户手动选择合集中的任意视频选择性播放」**。两种用法都要：放着不管它自己往下播，
和直接点第三集。

已确认的三个决定（2026-10-05，用户在 AskUserQuestion 里选的）：

| 决定 | 内容 | 为什么 |
|---|---|---|
| 入口 | **贴任意一集就行** —— 不需要用户去找合集页/番剧页那种"整包"地址 | 手机 App 的「分享」只能给出当前这一集。要求用户改成贴合集页地址，等于让他先搞懂 bilibili 的两种 URL 有什么区别 |
| 队列 | **队列在本机，懒解析 + 自动连播** | 一次解析 N 集 = N 次 `yt-dlp` + N 轮 ffprobe，而其中 N−1 集用户可能根本不看；且每一集的签名地址都短命（§4.14 里 `RESOLVE_JOB_TTL` 存在的理由就是"上一场的签名地址比没有地址更糟"）。懒解析把"识别全集"和"取某一集的字节"分开，前者只要一份 playlist JSON，后者复用今天的单集路径 |
| 交付节奏 | **本轮只写这份 spec**，实现单独一轮 | 合集涉及四个层（解析、队列、页面、连播判据），和本轮已交付的三件（两站解析修复、cookie 原话分类、mpv 标题修正）挤在一个 commit 里，出问题时分不清是谁 |

### 硬约束（来自 AGENTS.md，违反即返工）

1. 这一条落在**核心模块**（`macast/`），不是插件。理由和 §4.14 那条一样：要用的还是
   `yt-dlp` / `ffprobe` 两个外部命令，核心层已经这么做了；而**队列是播放状态的一部分**，
   它坐在 `DLNAProtocol` 里，插件层看不到它。
2. **不新增任何 pip 依赖**，不进 §4.4 的三处打包配置。这一条的全部新代码是 stdlib。
3. `Setting.get(key, default)` 有副作用（§4.2）：判存在用 `Setting.has`，删除用 `Setting.unset`。
   合集队列**故意不进设置 JSON**（见 §3.4）。
4. 每加功能同时补 `scripts/verify_cast_airplay.py` 用例，改完跑 pyflakes + 全量回归 + `--ci`。
5. **不为验证改用户真实配置**（临时 `SETTING_DIR` + 错开端口）。
6. 页面上每一个会漂移的数字必须问两遍（§4.13）：集数、正在播第几集、懒解析的时点，
   都由后端算出来，页面只渲染。
7. 中转门不变：`/relay/<随机 id>/media` 仍是随机 id + TTL，**不要**为合集发明一个"整包地址"
   把 N 集塞进一个路径（§4.14「中转链接不是保密通道」那句代价，集数越多越糟）。

## 1. 现在有什么，缺什么

### 1.1 核心已经有一个队列，但它只装地址

`DLNAProtocol` 在 `macast/protocol.py` 里已经维护 `self.playlist`（URI 列表）与
`self.current_index`，由 `AVTransport_SetAVTransportURI` 和 `cast_uri` 在每次投屏时追加，
并把 `NumberOfTracks` / `CurrentTrack` / `CurrentTrackURI` 报给控制点；
`AVTransport_Next` / `AVTransport_Previous`（`_playlist_step`）会真的切到邻集并**命名播放器**。

这条现成的通道给了"手选任意一集"一个标准出口：**任何 DLNA 控制点都能 Previous/Next**，
不需要我们再做一套私有 API。

它缺的只有两样：

- **每一集的名字**。队列里只有 URI，`title` 是"这一集投屏那一刻是谁给的"，
  而不是"这一集叫什么"。合集卡片要列出一集一集的名字，就得有一份和 playlist 等长的名字表。
- **播完自动往下走**。今天没有任何东西在"这一集播完了"的时候推下一集 ——
  `cast_uri` 会重建队列，但那需要有人（控制点、页面）再发起一次。

### 1.2 解析层今天是**故意**不开 playlist 的

两处闸门，都要在合集这一路明确绕过，而且必须只绕这一路：

| 位置 | 现状 | 合集要什么 |
|---|---|---|
| `media_resolve.py` 的引擎调用 | 带 `--no-playlist`（多 P / 合集只解当前这一集） | 合集识别需要**一次不带 `--no-playlist`** 的调用，才拿得到 `entries` |
| `parse_ytdlp_json()` | 只取 `entries[:3]` | 合集需要全部条目，且**只做轻量抽取**（地址 + 标题），不进度量表 |

第二条是"懒解析"的关键：`entries` 里的每一条对 bilibili 而言是
`https://www.bilibili.com/video/<bvid>`（**又一集页面地址**），不是签名直链 ——
所以它不需要 ffprobe、不进 `MAX_MEASURED` 配额、也没有 TTL 问题。真正取字节留到用户
（或连播）点那一集的时候，走今天已经验收过的单集路径。

### 1.3 已有的可复用形状

- **单集解析的整条链**（`ResolveJob`：scrape → ytdlp → measure → rank，卡片、轮询、
  错误四句话）—— 合集的每一集就是"再走一次这个"，一行不改。
- **自动连播的编排形状**在 `macast/plugins/renderer/cast_local_file.py`：
  看门狗线程 + `Auto_Next` 开关 + 队列 API（`enqueue` / `play_index` / `play_next` /
  `play_previous`）。**它的形状可以借，它的代码不能搬** —— 那是发送端，播的是电视，
  所以它靠每 5 秒 `GetTransportInfo` 判断"还在播"；我们这一路播的是本机 mpv，
  结束判据在 mpv 事件里，见 §3.3。
- **真集身份**只在一处存在过：`nirvana.py`（哔哩必连，vendored）的 `aid/oid/cid/epid/season_id`。
  本设计**不使用**那些字段，理由见 §3.2。

## 2. 设计一句话

**识别 = 一次不带 `--no-playlist` 的解析，只取"每一集的页面地址 + 标题"；
队列 = 核心里和 `playlist` 等长的一份名字表，本机内存、不落盘；
连播 = 播完这一集时由播放结束事件推下一集；手选 = 点第 N 集就是"对第 N 集的页面地址走一次单集解析并投出去"。**

数据流：

```
用户贴一集地址（bilibili 单集 / 番剧 / 合集页都算同一集地址）
  └─ POST resolve-page ──> 引擎（playlist 模式）答：N 条 entries
        ├─ 名字表 + 每集的页面地址  ──> SeasonJob（本机内存，一个）
        └─ 当前这一集 ──> 今天的单集候选表（完全不变）
  页面：「本合集共 N 集」卡片 + 每集一行按钮
        ├─ 「整包推送」：名字表 + 每集地址进核心队列，投第 1 集，`auto_next = True`
        └─ 「播这一集」：只对那一集走一次单集解析（= 今天的行为），并把它设为队首指针
  …… 本机 mpv 播完 ──> 播放结束事件 ──> 下一集的页面地址再走一次单集解析 ──> 投出去
```

任何一步失败都**只停那一集**，卡片说出是哪一集、为什么（§4.14 的"每一条失败必须给出门"）。

## 3. 组件与接口

### 3.1 解析层：`media_resolve.py` 加"合集"这一次读取，不加第二个引擎

新增一个函数（名字定在这里，§5.1 的 A 段用例按这个名字问，实现不许另起一个）：

```
season_from_ytdlp_json(raw_json) -> (title, [ (episode_page_url, episode_title), ... ])
```

- **输入是引擎已经返回的那一份 JSON**，不新起一次子进程调用。今天 `--no-playlist` 那一次
  已经拿到了单集结果；合集识别只需要**同一次调用的 playlist 形状**。
  实现方式（推荐）：一次调用不带 `--no-playlist`，然后把返回的 `info` 同时交给
  「单集候选」与「合集名字表」两个读取者 —— 少一次 spawn，且两个答案必然来自同一次网络往返，
  不会出现"卡片说有 12 集、投出去的是另一场解析的第 12 集"。
- **地址必须是页面地址**。判据是引擎自己给的 `webpage_url`；拿不到页面地址的条目
  **不进队列**（而不是进一个投不出来的空位），并在集数里如实少算。
- **只有真合集才成为合集**，判据只有两个，都写在函数里、由用例逐格问：
  ① 引擎这一份 JSON 自己是 playlist 形状（`info['_type'] == 'playlist'` 且 `entries` 是列表 ——
  今天 `parse_ytdlp_json()` 已经在按这个形状分支，`media_resolve.py:841`）；
  ② **可读的条目 ≥ 2**（"可读"= 这一条有自己的 `webpage_url`，见上一条）。
  因此"引擎把单集也包成一个 entry"那种通用形状（一条视频 → playlist 里一条）**自动不成为合集**，
  不需要按站点特判，也不存在一个虚构的"单集形状识别函数"。
  其余逐格：零 entry / 只有 entry 但都缺 `webpage_url` / 标题为空 ⇒ 都答"这不是合集"，
  而不是建一条投不出去的两集队列。
- **配额**：合集名字表**不占** `MAX_MEASURED` / `MAX_MEASURED_PER_HOST`（它们管的是"度量过的候选"）。
  但要有自己的上限常量：**`SEASON_MAX_EPISODES = 200`**。这个数不是量出来的，是**挑的**，
  挑的理由要写在常量旁边：一季 bilibili 番剧在几百集以内（最长的那批年更也在 100 上下），
  200 对真内容宽裕、对"贴一个 3000 集的站"是一扇门；而一份名字表只有 (页面地址, 标题) 两个字符串，
  200 条约几十 KB，**所以卡内存不是选这个数的原因，卡的是"允许谁把队列挂满"**。
  超了就只取前 200 条，并在卡片上**如实说出被截断了**（「本合集共 3000 集，这里只排了前 200 集」）。

### 3.2 为什么不用 `cid/epid/season_id`

`nirvana.py` 里那套字段是 bilibili 私有身份，要拿到它必须**读它的 API 并跟它的分页规则**。
本设计只用 `webpage_url`，代价与收益都要说清：

- **代价**：判"这两集是不是同一个合集"靠的是引擎给的同一段 playlist，不做跨合集去重；
  合集改名/换源后旧队列里的地址可能解不出 —— 那是一句如实的失败，不是一个错误。
- **收益**：机制**站点无关**（任何 yt-dlp 认的 playlist 形状都能建队），不引 bilibili 私有协议，
  不引凭据要求（§4.14 的 cookie 那两条限制一条都不新增），而且验证面只有"能不能解出那一集"。
- 因此**本期验证只在 bilibili**，但代码里不写 bilibili 专属分支。这一点要写在页面上吗？
  不写 —— 页面只说"这一条能不能整包投"，那是后端的答案。

### 3.3 队列与连播：`DLNAProtocol` 里的名字表 + 一个结束钩子

- **数据结构**：与 `self.playlist` 等长的名字表，随 `cast_uri` / `_playlist_step` 一起维护
  （现在这两处已经在写 `CurrentTrackTitle`，加一个并行数组是同一处改动）。
  合集会话额外带一个标志：`auto_next`（**这一次会话**要不要连播）。
- **连播的判据是"播完了"，不是"时间到了"**。本机的播放结束只有一个诚实来源：
  mpv 的 `end-file` 事件（`macast_renderer/mpv.py` 已经把它转成 DLNA 状态）。
  判据要点（实现必须逐条对上，用例逐条问）：
  - `reason == 'error'` **不算播完** —— 那是这一集投不出去，连着往下推会把 N 集全失败一遍
    （§4.2 那条"ERROR 例外"是同族教训）。
  - 换片时旧文件补发的那一次 `end-file reason=stop` 不算数 —— 和
    `MPVRenderer._note_stopped` 现在用的"当前媒体已经报过播放"同一个判据。
  - 用户主动 STOP / 被别的控制点抢占 / 投屏历史重投，都**不再自动推下一集**
    （被抢占时 `auto_next` 关掉，且这一句必须在页面上看得出来，否则用户读到的是"它自己断了"）。
  - 到合集最后一集播完就是**结束**，不循环、不停在最后一帧假装还在播。
- **推下一集 = 走一次单集解析**，不是"预先解析好排在这里"。实现上是同一个函数：
  拿那一集的页面地址，调今天 `_post_cast_resolved` 走的那条路径（解析 → 挑候选 →
  `open_relay` → 交渲染器），只是调用者是事件线程而不是 HTTP worker。
  **这一步不许在 CherryPy worker 上同步跑**（一次解析是几秒到几十秒）；
  也不许在 UI 线程上跑（§4.2 那条菜单线程纪律）。
- **失败的那一集要跳过并说明**：`auto_next` 遇到第 k 集解析失败 ⇒ 卡片那一行标失败 +
  原因（四句话之一，§4.14），并继续尝试第 k+1 集；**连续失败到 3 集就停下**
  （`SEASON_MAX_CONSECUTIVE_FAILURES = 3`，防一条断网把整个合集刷成 N 条同样的失败；
  3 是"一次断网能连续骗过三次"的经验数，和 `MAX_REPUSH = 3` 是同一个脾气，写在常量旁边）。
  停下时页面必须说"停在第几集、因为连着三集都没解出来"，而不是停在最后一行不动。
- **DLNA 控制点的 Next/Previous 照旧能用**，且和自动连播共用同一个指针 —— 两个主人是
  §4.14 明令禁止的那种状态分裂。

### 3.4 队列不落盘（决定，不是遗漏）

队列在内存，随应用重启消失。三个理由：

1. 那些 URI 是**签名地址**，明天恢复出来的是一条解不开的队列（`RESOLVE_JOB_TTL` 的同一句理由）。
   本设计里落盘的只有"页面地址"那一层，它确实能恢复 —— 但恢复出来的队列第一条该不该自动开播？
   这是一个用户没要求、而且要额外解释的功能。
2. `Setting.get` 的副作用（§4.2）让"存一个列表"这条路比看起来更滑；§4.11 明确把 list/dict 值
   划成"只读、引导去高级设置 JSON"。
3. 重启后重贴一条地址，代价是**一次复制**。

页面在队列空时不说"队列丢了"，只说"还没有识别出合集"（把"这是设计"读成"这是错误"是文案 bug）。

### 3.5 中转：每集一条，仍然只有当集在用

`RELAY_MAX = 8` 与"12 集的合集"**不冲突**，因为懒解析意味着**同一时刻至多两条**活跃中转：
正常是 1 条（正在播的那一集），换集的那一刻允许短暂 2 条（下一集的中转建起来、上一集还没摘掉）。
**2 是判据，1 是常态** —— 写用例时按 2 判，因为"先到 1 还是先到 2"取决于拆建的次序，
而那不是一个该由产品保证的事实；该保证的是**它不随集数增长**。
所以这一句要写成用例：建一个 12 集的队列后，活跃中转数 ≤ 2，**绝不是 12**。

每集一条 `/relay/<随机 id>/media`，门与 TTL 一律不变（§4.14 那三条红线一条都不动）。

### 3.6 页面：`setting.html`「状态」tab 的合集卡片

- **位置**：紧跟今天的「网页地址投屏」候选卡，同一次解析的产物，不另起一个入口。
- **出现条件**：解析层答"这是一条多集"，且集数 ≥ 2。单集时这张卡**根本不出现**（出现一个
  只有"就这一集"的卡片是噪音）。
- **内容**：合集标题 + 「共 N 集」+ 两个动作：
  - **「整包推送」**：投第 1 集并开 `auto_next`。
  - **每集一行的「播这集」**：只投那一集（等价于今天的单集行为，并把队列指针移过去）。
- **状态**：正在播第几集、已跳过的集（带原因短句）、`auto_next` 当前是开还是关（关的话，
  是用户关的还是被抢占的）。
- **进度条沿用 `ResolveJob.STEPS`**（Part 59 Q 段的文本契约）；连播时那一集的解析进行中，
  卡片上必须看得出来是"第 k 集正在解析"，而不是整个合集在转圈。
- **禁止**：页面不许自己数集数、不许把"第几集"算出来、不许出现 bilibili 专属措辞以外的猜测。
  帮助弹层要同步加一段（§4.13：新增能力必须写进帮助，且数字问两遍）。
- **`v-html` 一律不许出现在这张卡**：标题来自那页 HTML（§4.10 那条注入面在这张卡同样成立，
  而且合集标题更容易被投毒，因为它是发送端提供的）。

### 3.7 门与凭据

- 新端点全部走 §4.7c 的 `Handler.POST_ROUTES` 表，门 = **`GATE_MANAGEMENT`**（和
  `cast-uri` / `cast-resolved` 同一档；它们不落代码，只是投屏）。GET 版（若有）按 §4.7
  要求令牌。
- 不新增任何凭据面：合集的 cookie 需求就是单集的 cookie 需求，那两条路（粘贴 jar /
  从浏览器读）已存在，**不改动**。
- 要登录的合集这一期**仍然解不出**（§4.14 的"需要 JavaScript 才算得出地址的站点"照旧；
  需要会员 cookie 的番剧，粘贴那份 jar 之后能不能解出**没有验证过**，写在页面的"未验证"边界里）。

## 4. 边界（明确不做，且写在页面上）

| 不做 | 理由 |
|---|---|
| 一次解析全集 | 已批准的决定（§0）；代价是"下一集要等一次解析"，页面上要说这一句 |
| 跨站点合集去重 / 分季合并 | 依赖 bilibili 私有身份（§3.2） |
| DRM / 受保护内容 | 全站不可能（§9） |
| Macast 代用户登录 | §4.14 已定，合集不开新口子 |
| 队列落盘 / 重启续播 | §3.4 |
| 把 N 集拼成一个中转路径 | §3.5，且那是"转发出去别人能读一整季"的更大暴露面 |
| 预取下一集的字节 | 签名地址短命 + 磁盘/带宽代价，而收益只在"网络比解析快"时成立 |
| 非 bilibili 站点的真机验证 | 机制站点无关，验证只在 bilibili（§3.2） |

## 5. 验证计划

### 5.1 套件（**新 Part 63**；当前最大是 Part 62 = mpv 投屏标题那一轮，编号接在它后面）

按"这个事实住在哪一层"分段，每段测的是**决定它的那一处**：

| 段 | 测什么 | 关键判据 |
|---|---|---|
| A 合集识别 | `season_from_ytdlp_json()` 的输入形状（**全部喂 fixture，不碰网络不 spawn**） | 单 entry 不许冒充合集；缺 `webpage_url` 的条目不进队列且集数如实少算；`SEASON_MAX_EPISODES` 截断要说出来；名字表与地址表等长 |
| B 一次调用两个读者 | playlist 模式那一次调用的输出同时喂单集候选与合集名字表 | `--no-playlist` 那一路的既有行为一字不变（Part 59 的现有用例必须继续绿，这是回归的主要牙齿）；名字表不占 `MAX_MEASURED` |
| C 队列与名字表 | `cast_uri` / `_playlist_step` 之后，`playlist`、名字表、`CurrentTrack*` 三者一致 | 三个读者的指针同一个；Next/Previous 仍按现有契约（Part 62 的用例不许被改宽） |
| D 连播判据 | `end-file` 的每种 `reason` × 每种媒体状态 | `error` 不推下一集；换片时的旧文件 stop 不推；被抢占后 `auto_next` 关且不再推；最后一集播完是结束 |
| E 跳过与上限 | 第 k 集解析失败 | 失败原因走 §4.14 的四句话；继续试 k+1；连续失败 3 集就停下，并说清停在第几集（`SEASON_MAX_CONSECUTIVE_FAILURES`，§3.3） |
| F 中转数量 | 12 集队列的活跃中转数 | ≤ 2，绝不是 12（§3.5） |
| G 页面文本契约 | 卡片出现的条件、集数与"第几集"来自后端、`c.<key>` ⊆ `describe()` 的键、进度条读 `ResolveJob.STEPS`、全卡无 `v-html` | §3.6 的每条禁令各一条；帮助弹层与卡片说同一句话（§4.13） |
| H 门 | 新端点在表里、门 = `GATE_MANAGEMENT`、局域网无令牌 403 且那条路由一次都没被调用 | 按表循环（Part 51 的形状），不许手写点名 |

**变异体（每个单独跑完整套件，还原后 md5 逐字节校验，绝不 `git restore`）**：至少覆盖
删掉"单 entry 不算合集"那一问、把 `error` 也算播完、抢占后不关 `auto_next`、
名字表和 `playlist` 只维护其一、页面自己数集数、卡片用 `v-html`。
每个变异体都必须红在**它自己那句话**上，红集互不相交。

### 5.2 真机（这一步不能由套件代替）

临时配置目录 + 错开端口的第二台实例（**绝不碰用户 58880 上那个**）：

1. 贴一个真 bilibili 多 P 地址，卡片必须报出**真实集数**（和页面上数出来的一致）。
2. 点「整包推送」→ 第一集在本机 mpv 播起来 → **不碰任何东西**，等它播完 →
   下一集自动解析并播起来，窗口标题跟着换（这一条同时验 D 本轮的标题修正）。
3. 中途点「播这集」跳到第三集，队列指针与 `CurrentTrack` 必须一致。
4. 中途让另一个控制点投屏（或 POST 一条别的地址）→ 连播必须停，且页面看得出来。
5. 三档宽度（520 / 1000 / 1680）各截图一遍，控制台零 JS 报错。
6. 一条需要会员的番剧地址**试着解一次**，把结果如实记进文档（解得出与解不出都是答案；
   这一条是 §4 最后那行的欠账，不许用"理论上应该要 cookie"代替测量）。

### 5.3 仍未验证的边界（写进文档，别读成已验收）

真 Chromecast / 真老电视仍然欠着（§4.14 末那条欠账不因合集而改变）；
非 bilibili 站点的合集机制上支持、实际没人验过。

## 6. 落地顺序（每步都可独立测试并推送）

1. 解析层：一次调用两个读者 + `season_from_ytdlp_json()` + 上限（A、B 段用例 + 变异体）
2. 核心：名字表与指针（C 段）
3. 核心：连播判据与跳过（D、E 段）——**这一步是这一条功能的真实风险所在**
4. 页面：卡片 + 帮助同步（F、G 段）
5. 门与端点登记（H 段）
6. 真机六问（§5.2）+ `--ci` 对齐 + 文档同步（§4.14 新增一段、`docs/Casting-Suite.md` 新增一节）

第 1 步做完就可以单独跑一次套件；第 3 步之前不要动页面（否则卡片驱动的是一条还不存在的连播）。
