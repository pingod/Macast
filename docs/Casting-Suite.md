# Casting Suite 使用指南（发送端插件族）

面向**使用者**：怎么把这台电脑的屏幕、声音、本地文件弄到电视上，以及反过来
怎么让 iPhone 把屏幕镜像到这台电脑。规划与取证件见
[`Casting-Suite-Plan.md`](Casting-Suite-Plan.md)，实现层的红线见 `AGENTS.md` §4.8，
插件的安装与索引机制见 [`../plugins/README.md`](../plugins/README.md)。

> **诚实声明**：下表每一个"目标"都只在**打桩测试**（`scripts/verify_cast_airplay.py`）
> 与自家假设备/假电视上验证过。**真实 Chromecast、真实老电视、真实 iPhone 一台都没碰过。**
> 每条链路末尾都标注了它的验证状态和现场排障入口。

## 0. 先决条件（三件插件都共用）

| 需要 | 为什么 | 装法 |
|---|---|---|
| **ffmpeg** | 屏幕镜像与转码全靠它 | `brew install ffmpeg`。插件会按 PATH + `/opt/homebrew/opt/ffmpeg/bin` 等常见目录找（**从 Finder 启动的菜单栏 App 不继承 shell 的 PATH**，所以只写在 `~/.zshrc` 里不算数） |
| **ffprobe** | 本地文件投屏判断"直通还是转码" | 随 ffmpeg 一起来 |
| **屏幕录制权限**（macOS） | 没有它 ffmpeg 一秒内退出 | 首次失败时插件会提示去「系统设置 → 隐私与安全性 → 屏幕录制」勾选 Macast，**勾完要重启 Macast** |
| 同一局域网 | 电视要能反过来访问这台电脑 | 代理变量会被自动摘掉（否则局域网流量走代理 → 502），见 `AGENTS.md` §4.1 |

**渲染器互斥**：`Local File Caster`、`Chromecast Bridge`、`Floating Player` 等是 renderer
类插件，**同一时刻只能启用一个**，在菜单栏「选择播放器」里切换 —— 那一栏决定的是
**收到投屏时用什么播放**。`AirPlay Audio (RAOP)` 与 `AirPlay Screen Mirror`
是协议类插件，可与任意渲染器共存。
**电脑投屏不属于这一栏**：它不需要先"切到 Screen Mirror"，菜单栏「打开设置页」在任何渲染器下
都点开同一个页面（详见 §1）。

**装插件**：**只有手动安装这一条路**（2026-09-21 所有者已定：`pingod/Macast` 继续私有，
不再讨论"改公开 / 另立公开仓库"）。未登录的浏览器和 Macast 的匿名下载都读不到私有仓库，
所以设置页「插件」页里的「可安装」卡片对别人只是展示，点下去会失败。走这两条：

1. 设置页（<http://127.0.0.1:58880/>）→「插件」→ 在输入框里贴一个**你这边可达的** `.py` 直链 →「从网址安装」；
2. 或直接把 `.py` 放进 `~/Library/Application Support/Macast/renderer/`（协议类放 `protocol/`）——
   **放完即热生效，不用重启**（手工放进的目录需要有个 `__init__.py`，装过任一插件就有了）。

想确认自己这台机器上到底通不通：`python scripts/check_index_reachability.py`，
私有状态下稳定报 `INDEX_PRIVATE`（退出码 2）**是预期信号，不是待修的 bug**。

## 1. Screen Mirror —— 把这台电脑的屏幕推出去

菜单栏点 **「打开设置页」**（或直接开 `http://127.0.0.1:<端口>/?page=13`）进入设置页的
「电脑投屏」页签。它不属于「选择播放器」那一栏：当前用哪个渲染器都点得开，
也不需要先把 Screen Mirror 选中。

**投屏的控制全在页面里，菜单栏一项都不放**（2026-09-23 所有者定：菜单只留通用功能，
镜像的开关、目标、画质、设备列表都在页签上）。从「正在采集你的桌面」里出来有三条路，
都不要求你恰好还开着那个页签：

1. 页签右上角的 **「停止镜像」**；
2. 菜单栏 **「停止接受投屏」** —— 停掉整个服务，渲染器随之 `stop()`，采集与推流一起收尾；
3. 菜单栏 **「设置 → 选择播放器」** 切到别的渲染器 —— 同样触发 `stop()`。

后两条走的是 `ScreenMirrorRenderer.stop()`，与页签上那颗按钮终止的是同一场清理
（`_teardown`，含释放 `caffeinate` 休眠断言）。

页签里的卡片（区块按当前协议增减）：

```
投屏方式   每种协议一行：Chromecast · 低延迟 · DLNA 电视 · 浏览器 · WebRTC 低延迟，
           各自写着自己那轮搜索的结论，行内就能选设备
设备       选中协议的机器列表 ＋「重搜设备」
还缺什么   只在依赖没满足时出现，写清缺什么、怎么装（命令可复制）
兼容档位   仅 DLNA 协议
画质       四档
采集       这台电脑：显示器 / 指针 / 编码器
系统声音   macOS 一键设置 · Windows 探测回环录音设备
观看地址   浏览器与 WebRTC 目标才有 ＋ 复制
预览       这台电脑当前的采集画面，约 1 fps 一张
活动       连接、断开、档位回退、权限被拒、编码器退出（最近 20 条）
统计信息   这次会话的原始数据：延迟由哪几项相加、真实 ffmpeg 命令行、发现逐网卡尝试（开始镜像后才出现）＋ 一键复制
```

- **先问协议，再问设备**：「投屏方式」列出这台机器的插件**能驱动的每一种协议**，
  各带自己那轮搜索的结论，一共五句，每句说的是不同的事实：
  「发现 N 台」/「发现 N 台（另有 M 台应答了发现但读不到描述，已跳过）」/
  「正在搜索局域网设备…」→「正在重新搜索…」（只有**第一次**还没搜完时才是前一句）/
  「还没有搜过」/ 或者搜索本身失败的原因。搜完而空手的三句各自点名下一步该做什么：
  「没有发现 DLNA 电视：局域网里只有这台 Mac 自己的接收端，已排除；电视需要和这台 Mac
  连同一个网络才会应答，确认后点「重搜设备」（搜于 …）」/
  「有 N 台设备应答了发现，但都读不到描述：通常是它在休眠，或者固件不报 AVTransport。
  唤醒它或在它上面打开 DLNA/投屏，然后点「重搜设备」（搜于 …）」/
  「没有发现 Chromecast；如果设备就在这台 Mac 的同一个网络里，检查它是否开机、
  再点「重搜设备」（搜于 …）」。
  「只有这台 Mac 自己」这一种值得单独说：Macast 自己就是一个 DLNA 接收端，所以电视关机时
  SSDP 往往**仍有应答**，而应答的是这台 Mac —— 以前它和"局域网彻底没人"印成同一句
  「没有发现」，于是搜索到底坏没坏只能靠猜。
  空的 Chromecast 答案不代表 DLNA 那边也没有电视，
  浏览器协议根本不问设备（那一行写「不需要设备」）。以后自研一种接收协议，
  是**加一行、加一个搜索**，页面不用改。
- **一轮搜索做两件事**：M-SEARCH **发两次**（一次不算搜完：刚睡醒的设备还没加入组播组，
  单包会让设备列表取决于它那次 join 恰好落在哪个 100 ms 里），且**钉住网卡时**用
  `IP_MULTICAST_IF` 指定组播出口 —— 只绑源地址等于把路由查表留给内核，那正是虚拟机网桥
  把搜索带走的那条路（AGENTS.md §4.1 对 mDNS 记过同一个坑）。设备描述有 3 秒超时，
  上一轮的结论每轮重来，不会赖在页面上。
- **需要装的东西不会被通知吃掉**：任何插件说「去装 X」，同一句话（含可以复制的命令）
  会留在「还缺什么」卡片上，直到那个依赖真的被满足 —— 通知五秒就没了，这张卡不会。
- **区块是按需长出来的**，不是"全列出来再灰掉"：Windows 没有 BlackHole 可装，浏览器协议
  没有兼容档位可选 —— 永远点不动的行看起来像坏掉的页面。
- **改任何一项都是"提交后重读"**：档位可能被看门狗自己换掉、编码器可能刚死，所以没有乐观更新，
  页面每秒读一次状态。
- **预览是快照不是视频**：约 1 fps 向应用要一张 480px 宽的桌面图。取不到时留着上一张并写明原因；
  **镜像进行中预览直接站下来**，卡片写「镜像进行中」——同一块屏幕开第二路采集只会耗满
  超时然后什么都没有，宁可少一张图。
- **页面关掉不影响正在进行的投屏**：观看端各自持有自己的会话，页签只是这台电脑的控制面与读数；
  要从采集里出来，见本节开头那三条路。
- 插件日志在 `logs/ScreenMirror.log`（设置页 →「日志」下拉里选）。

五个目标共用同一份采集与编码，区别只在**封装**和**怎么交给对方**。

### 1.1 协议：Chromecast / Google TV（默认，兼容通道）

首次设置：

1. 「投屏方式」→ **Chromecast / Google TV** 这一行。
2. 在这一行（或下面的「设备」列表）里选一台。该行右侧会写清这一轮搜索的结论（本节开头
   那五句之一），点「重搜设备」重来一次。一轮搜索真的要等：Chromecast 那侧 mDNS 问 2 秒，
   DLNA 这侧 SSDP 问 2.5 秒、再逐台拉描述（每台上限 3 秒）—— 页面因此不会假称搜索完成，
   没搜过之前那一行写的是「还没有搜过」。
3. 点右上角「开始镜像」。插件走 deviceauth → CONNECT → LAUNCH → LOAD，
   把一条 `http://<本机>:<端口>/stream/<随机id>.ts` 的**实时 MPEG-TS** 推给电视。

列表里不会出现这台 Mac 自己：Macast 的 Chromecast 接收端广播的正是
`_googlecast._tcp`，不滤掉的话第一条就是"投给自己"，那是个回环不是目标。

现场读法：页脚那一行报「已镜像 · 码率 · 观看端数 · 丢块数」，右栏的预览就是电视此刻看到的画面。
**丢块在涨是正常的**（慢消费者丢整块，绝不阻塞编码器）；码率明显低于档位设定值
在 v0.23 之后**不再自动等于"编码器跟不上"** —— 各编码器对档位码率的承诺不一样，见 §1.6
「编码器」那一节。真跟不上时画面会先卡，不会只在码率上留证据。

这一路发送端自己贡献的延迟是**约 0.8 秒**（每个观看端的队列按"存多少秒画面"预算，
见 §1.6），电视端解码与缓冲另算 —— **这一路的端到端延迟没有在真电视上量过**，
所以页面与提示里只报我们自己那一段。

这一路**受「投屏最大时长」约束**（三档，到点主动停止并弹一条点名那个开关的通知）。
浏览器页与两条低延迟通道不受它管；为什么只管电视、以及那个数怎么同时管住 `-t` 与
「伪装成文件」声明的长度，都写在 §1.6 末。

排障：电视黑屏但状态行有码率 ⇒ 看 `ffmpeg` 是否只推了音频；
日志在 `~/Library/Application Support/Macast/logs/ScreenMirror.log`（设置页 →「日志」下拉选它）。

### 1.2 目标：Chromecast 低延迟（Cast Streaming，实验）

同一条 Chromecast，换 Chrome「投射桌面」用的那套协议：不 serve HTTP、不发 LOAD，
LAUNCH 镜像接收器 `0F5096E8` → OFFER/ANSWER → **UDP 上推 RTP**。

- **设备不认就直接回落** 1.1 的 LOAD 通道，不需要你拆摊子重来。开始的那条通知会写明
  「设备拒绝了低延迟通道（…），已改用兼容通道 LOAD，这一路有声音」。
- **这一条通道本身没有声音**（「投屏方式」里那一行就写着「实验 · 此通道无声音」）。
  这里有一个容易混过来的读法：如果你点了它却**听见**了声音，那不是这一条通道在出声，
  而是电视拒绝了它、已经默默换成 1.1 的 LOAD —— Cast Streaming 的 RTP 里只装了视频。
  分辨方法：看状态行，低延迟通道报的是「在途 / 丢帧」，LOAD 通道报的是「观看端数 / 丢块数」。
- **码率上限 8.0 Mbps**（`CAST_STREAM_MAX_BITRATE`），天花板是**加密速度**而不是网络。
  2026-10 之前这一格写的是「4.5 Mbps，因为纯 Python 的 AES-128-CTR 只有约 1.3 MB/s」——
  那时是真的。现在加密走**操作系统的原生 AES**（macOS CommonCrypto / Windows bcrypt /
  Linux libcrypto，ctypes 调用，**没有新依赖**），比纯 Python 快约 4000 倍：按真实链路的形状量
  （复用一个句柄 + 每帧重算 counter block + 41,667 字节的一个访问单元）是 **5,367 MB/s、
  每帧 7.8 µs**，纯 Python 同一个负载是 1.35 MB/s。所以那个上限从「物理天花板」变成了
  **我们自己选的一个数**：
  8 Mbps 对齐 Google 参考发送端的 `kDefaultVideoMaxBitRate = 10 Mbps` 与 Chrome
  标签页投屏默认的 5 Mbps 之间，取一个 1080p 够用、又不至于让电视解码端吃紧的值。
  纯 Python 的密钥流仍在，只是**降为最后的兜底**（三个后端都拿不到时），那时会退回
  `CAST_STREAM_DEGRADED_BITRATE = 4.5 Mbps` 并在「投屏方式」那一行与「画质」下面写明
  「已自动降级」。设置页那行提示里的加密后端名字是**运行时问出来的**，不是写死的。
  选 1080p/原始分辨率仍然不会更快：帧尺寸会被信箱化到一个固定尺寸，提示会写明上限。
- 状态行多两个字段：**在途**（设备还没确认的帧数）与**丢帧**
  （因窗口满而整帧丢弃的张数）。在途的上限**不再是固定的 12 帧**，而是按
  `clamp(2 × RTT, 66 ms, targetDelay/3)` 算出来的时长窗口（另有 120 帧的硬顶防跑飞），
  本机 24 fps 下 66 ms ≈ 1.6 帧。旧的 12 帧在 24 fps 下等于 **500 ms 的排队**，
  是协议自己那份 200 ms 延迟预算的 7.6 倍 —— 那才是「低延迟通道」排在队里的大部分时间。
  在途长期贴着上限 ⇒ 设备消费不动，回落 1.1。
- **丢包会被补**（v0.19 起，此前这一条写着「没有重传路径」，那句是把 openscreen 读成了
  「只检测、不修复」）：设备在确认帧的**同一个** RTCP 包里点名缺哪些包，我们把它们重发一次
  —— 复用原来的密文、只换 RTP 序号，所以线上不会出现两个相同序号。
  设置页「统计信息」因此多三行：**往返时延**（就是它决定上面那个窗口有多大；还没有任何
  确认时读「暂无」，那不是「0 毫秒」）、**补发**（补出去的包数）、**未补发**
  （只在非零时出现，两种原因：包**太新** —— 按 openscreen 的规则，发出还不到一个 RTT 的包
  不算丢，补它只是在一条已经拥塞的链路上再灌一份；或者那一帧已经被 **8 MiB 修复缓冲**
  挤出去了）。怎么读：**`补发` 非零而 `丢块` 为零 ⇒ 无线在丢包，这条路径正是在为它工作**；
  `补发` 与 `丢块`（这一路数的是被窗口整帧丢掉的张数）一起涨 ⇒ 链路拥塞，回落 1.1。
  **别拿「实际送达 − 编码器产出」当补发流量**：这两个计数器**没有固定大小关系** ——
  前者数数据报（每个比载荷多 19 字节）外加补发与空闲探测，后者在窗口判定**之前**就加了，
  被丢掉的帧也算在内。所以丢帧的流是「编码器产出」领先，不丢帧的流是「实际送达」领先。
- **验证状态：未经任何真实电视验证。** 字段布局是从 openscreen 转写的，
  打桩测试只证明字节自洽。第一次上真机请用探针，它 `import` 的就是插件本体：

  ```shell
  .venv/bin/python scripts/cast_streaming_probe.py --live   # 采真桌面
  .venv/bin/python scripts/cast_streaming_probe.py --source /path.mp4 --dump /tmp/out.h264
  ```

### 1.3 目标：DLNA 电视（没有 Google 栈的老电视）

Macast 把一条**直播流**推给电视：告诉它播哪个地址，然后一直喂字节。

**投屏形状**（2026-09-23 起，多了一行「投屏形状」，排在「兼容档位」上面）决定怎么描述它：

| 形状 | 它怎么答 | 什么时候用 |
|---|---|---|
| **直播流**（默认） | 200、不报 `Content-Length`、`Accept-Ranges: none`；客户端要偏移就给当前直播点 | 现代电视与播放器（Android TV、mpv、Kodi） |
| 伪装成文件 | 报一个 <2 GiB 的假长度、承诺可拖动（`Accept-Ranges: bytes`），尾部探测回 416 | **只认有限文件**的老电视 |

**为什么默认换成直播流**：同一台机器、同一个编码器，测出来的差别是决定性的。

- 直播形状：mpv 报 `vo-configured`、H.264 1680×1080、**进度在走**（0 → 19.5 秒），能播。
- 伪装成文件：mpv 与一台 TCL Android 11 电视都**读完整条流、再请求「伪造结尾前 250 KB」**
  ——那是客户端的容器索引探测——拿到 416 之后**从头重来**，看门狗重投到第 8 次放弃，
  `GetTransportInfo` 始终不是 `PLAYING`。

那个伪造的长度本身就是在邀请客户端去读一个不存在的尾部索引。只认有限文件的老电视仍然可以
**切回「伪装成文件」**（那条路是为它们留的），但现在的默认是能播的那一种。

首次设置：

1. 「投屏方式」→ **DLNA 电视**，在这一行的设备列表里点一台。
2. 「投屏形状」保持 **直播流**；只有在电视不播、而且确认它是老机型时才试「伪装成文件」。
3. 「兼容档位」再按电视年代选（见下）。
4. 点「开始镜像」。

五档按"老电视可能性"从高到低排：`ps-pal` / `ps-ntsc`（北美、日本老电视）/
`ts-mpeg2`（认 TS 不认 PS）/ `ts-h264` / `mkv-h264`（只认 MKV 的电视、Kodi）。

**从没动过「兼容档位」的安装，默认值随「投屏形状」走**：直播形状用 `ts-h264`，
「伪装成文件」用 `ps-pal`（那一档本来就是为 DVD 时代的固件留的）。这是量出来的，不是手感：

| 档位 | 首帧 | 稳定落后 |
|---|---|---|
| `ts-h264`（直播形状默认） | 2.0 秒 | 1.9 秒 |
| `mkv-h264` | 2.4 秒 | 2.1 秒 |
| `ts-mpeg2` | 2.5 秒 | 2.2 秒 |
| `ps-pal`（伪装成文件默认） | 5.7 秒 | 5.1 秒 |
| `ps-ntsc` | 5.7 秒 | 5.0 秒 |

**这张表的接收端是本机另一台 mpv / Macast，不是真老电视** —— 设置页把这句限定和每一档一起
显示（鼠标停在档位上也看得到）。"TS 比 PS 快约 3 秒"这个顺序是通用的：`ps-pal` 与 `ts-mpeg2`
在这里跑的是**逐字节等价的载荷**（同为 MPEG-2 + AC-3、同码率、同 25 fps、同 720×576），
差的 3 秒完全来自容器 —— MPEG-PS 自我确认很弱（`ffprobe` 给它的 `probe_score` 是 26，
TS 是 100），接收端不确定手里是什么就会再多缓冲 1.1–1.4 秒才敢开播；而且开局晚 3.4 秒
就全程晚 3.4 秒（两边位置都以 1.00x 前进）。这几秒具体是多少是**这一台**接收端的数。

看门狗每 5 秒问一次 `GetTransportInfo`，电视掉出 `PLAYING` 就重投；`RelTime` 在动才算活着。
**连续被拒会自动换下一档** —— v0.17 起是真的换，不再只是提示你手动换（用户的眼睛在电视上，
不在设置页）。一次镜像最多换 4 档（从任何一档起步都走得完其余四档），每档重启一次编码器，
通知里说清换到了哪一档、这是本次第几档。三条边界都有理由：

- **不改你在设置页里选的档位**：阶梯只活在这次运行里，重新开始镜像就回到你选的那一档。
- **「伪装成文件」形状下不换档**：那里的问题是形状本身（电视拿到的是一个伪造的长度，
  它会去文件尾部找一个不存在的索引），换五个容器也换不出答案，提示会直接叫你换形状。
- **只有证据指向"容器被拒"时才换**：即"连续几次没播起来"与"取走了地址却一个字节都不读"
  这两种；网络断了、电视不答 `GetTransportInfo` 都不算，那些换档也没有用。

五档走完仍没播起来，会说"本次镜像已经自动换过 4 档封装，它一种都没有接受"，
并把人指向「投屏形状」—— 而不是把"换成下一档试试"再重复一遍。

- 「伪装成文件」形状下，开始镜像要先攒**约 4 秒画面**再交出去（按档位码率算，夹在 2–8 MiB
  之间），否则电视开局那次探测会判定文件坏了；**直播形状不需要预填**。
  **这 4 秒现在是「投屏形状」卡上的一个旋钮**（1 / 2 / 4 / 6 / 8 秒，`Mirror_Dlna_Prefill`），
  改它会重启镜像。之所以做成旋钮而不是把默认值调小：**这个数字就是这一路看得见的延迟**
  —— 电视先攒够它才开始播，然后一直慢这么多、不会追上来 —— 而"多小才不会被老电视判成
  坏文件"这件事**本机量不出来**（没有那样的电视）。参考项目 MirrorCast 在一台真的
  Philips 43PFS5301（2016，非 Android）上预填约 20 MiB、也就是 20–25 秒，还明说了这一点，
  所以"比我们下限要求更多"的固件确实存在。一个量不出来的数，就交给能量它的人。
- 和 Chromecast 兼容通道一样，这一路**受 §1.6 末那条「投屏最大时长」约束**；那个上限还参与
  「伪装成文件」那对 `size=` / `duration=` 的算法（只会被它缩短，不会被它拉长）。
- 状态行：`已镜像 m:ss · 档位 … · 电视 … · 缓冲 … MiB`。「电视 未上报」意味着它连
  `GetTransportInfo` 都不答 —— 换形状或换档位。
- 「伪装成文件」形状的观看地址**会重放**（按绝对字节偏移从环形缓冲里取），因为电视会 HEAD、
  探边界、断线重连同一偏移。直播形状不重放（重放 = 客户端从此慢几秒）。
- **验证状态**：直播形状**已实测**——本机 mpv 端到端（判据是 mpv 自己的 `vo-configured`
  与 `time-pos` 在走），以及 Windows → macOS 的整条链路。上面那张延迟表同样是**打这台
  mpv / Macast 量出来的**。**电视侧仍未复验**：手边那台 TCL
  属于"应该用直播形状"的现代设备，但还没在这台电视上跑过新一轮。
  只认有限文件的老电视那条路，历来只有打桩测试，没有真机。
  **自动换档这条新路径同样只有打桩测试**：用例把整条阶梯走完（每一档重启一次、生成号先增
  后拆、用户的设置一个字节没动），但"电视真的因为换档而播起来了"没有在真机上验证过。


### 1.4 目标：浏览器（任何一台能开网址的设备）

不装任何 App：局域网里的电脑/平板/手机浏览器打开一个网址就能看。

1. 「投屏方式」→ **浏览器（打开网址即可看）**，点「开始镜像」。
2. 右栏「观看地址」会出现地址本身（形如
   `http://<本机>:<端口>/browser?token=<每会话随机>`），下面两个按钮分别是
   「复制」和「在本机浏览器打开」。粘到目标设备的浏览器。
3. 页面里是 fragmented MP4 → MSE 播放；没有 MSE 的浏览器自动回退渐进式 `<video>`，
   并在顶栏**写明回退的原因**（这一条以前不写：`addSourceBuffer()` 只认 MIME 形式的
   编码声明，页面递给它裸的 `avc1.640028,mp4a.40.2`，于是**每次**都抛
   `NotSupportedError` 后静默回退 —— Chrome 还能出画面，Safari 就是一片黑）。
   **v0.23 起那个 `avc1.…` 不再是写死的**：四字符码从编码器真产出的 init segment 里读
   （`moov` → `avcC` 的前三个字节，读不懂就回落到默认声明）。这不是美化 ——
   **软件档（x264）从来就不是 `avc1.640028`**，它交出来的是 `avc1.42c028`（1080p），
   720p 是 `avc1.42c01f`、2160p 是 `avc1.42c033`；`avc1.640028` 只在"VideoToolbox +
   1080p + 不钉 level"和"NVENC + 1080p"这两种形状下才是对的，而后者是**巧合**：同一台
   Windows 上同一个 NVENC 换到 2160p 就交 `avc1.640033`（这一对是 2026-10-03 在那台机器上
   读出来的，x264 的三行则在 Mac 与 Windows 上各读一遍、逐字相同）。三个读它的地方（播放页的
   `addSourceBuffer`、观看页浮层的「H.264 Profile」、设置页「统计信息」卡片）
   拿的是**同一个答案**，它错就三处一起错，所以它必须由线决定而不是由文档决定。
4. **声音默认是关的**：浏览器自动播放策略要求"静音起播"。点页面右上角
   「开声音」按钮，或直接点画面任意处（任何真实手势都算同意）。
5. 晚加入的观看端会先拿到 init segment + 最近 8 MiB 尾部，所以能中途接入。
   **丢包的单位是"整个片段"**（一个 `moof` 加它自己的 `mdat`）：以前按字节块丢，
   慢消费者会拿到半截片段或没有 `moov` 的裸 `mdat`，Safari 直接一片黑、
   连"正在缓冲"都不报（2026-09-23 修，`screen_mirror._Fragments`）。
   尾部从**最新的、以关键帧开头的那个片段**开始（v0.19）：分片切成每帧一片之后，
   封装器不再保证"一个片段以 IDR 开头"，所以发送端逐片做真关键帧检查
   （`starts_with_keyframe`，读不准一律当"不是"）；一个能当起点的都没有时，
   这个观看端**不从尾部拿旧字节**，而是从下一个关键帧开始 —— 喂一段从 P 帧开头的
   残片只会得到花屏。
   v0.19 之前这一段的代价是约 0.5 秒（首帧要等一个 GOP 长的片段封完），
   现在一个片段 = 一帧 ≈ 41.7 毫秒（24 fps）。
   **v0.23 起这次"没有可播起点"是一件会说出来的事**：环里一个 IDR 开头的片段都没有时，
   计数加一（`keyframe_misses`），观看页浮层与设置页「统计信息」卡片各自显示
   「重播等关键帧 N 次」，而**两处读的是同一个数**。它回答的是"这个观看端为什么黑了一下"：
   N 在涨 = 尾部确实没有可播起点（关键帧太稀或积压太浅），N 不涨而仍卡 = 问题在别处
   （看「发送端丢块」那一条）。
6. 页面顶部条会显示延迟/缓冲状态；播放页把自己停在**直播边缘后面 1 秒**（`LIVE_EDGE_SECONDS`，
   2026-10 之前写死 3 秒），缓冲区超出就跳回这个位置。
   **它是「观看页」卡上的一个旋钮**（0.5 / 1 / 2 / 3 / 5 秒，`Mirror_Live_Edge`），
   而且是这里唯一一个**改完不用重启镜像**的：这个数是发页面时注进 HTML 的，所以刷新观看页就生效。
   **v0.19 起它的含义从"延迟旋钮"变成了"恢复距离"**：分片切成每帧一片之后，
   停在边缘后 0.5 秒与 1 秒实测只差 9 毫秒（829 / 838，噪声内）—— 真正的延迟由分片粒度
   决定，这个数现在管的是"卡顿后（`STALL_MS = 8000` 毫秒整页重载前）手里还留多少余量"，
   所以默认值没动。下限仍是 0.5 秒而不是 0：停在 0 秒就是**正好压在写入头上**，
   编码器打一个嗝就是一次卡顿。
   **v0.18 曾写"分片节奏是 `FPS // 2 = 12 帧 = 0.5 秒`，所以 `+frag_every_frame` 买不到
   东西"—— v0.19 用真浏览器探针推翻了它**（`scripts/mse_latency_probe.py`：真采集 +
   硬件编码，同一个 `-g 12` 只把封装器的分片粒度从"每关键帧"切到"每帧"）：
   端到端 lag p50 **1305 → 838 毫秒（−36%）**，画质同值（VMAF 94.42），
   字节只多约 1%。代价不是带宽，是上面第 5 条那条新契约（分片不再保证以 IDR 开头）。
   更密的 `-g 2` 单独否掉：码控被抽干、画质 93.9 → 81.1，买到的延迟远不值这个价。
7. **推流统计浮层**：点顶栏「统计」（和「开声音」「全屏」并列）在画面左上角展开一块
   YouTube「详细统计信息」那样的面板，再点一下收起；**这个开关记在观看端自己的浏览器里**
   （`localStorage`），发送端不用改任何设置，也不需要重启镜像。面板分三组：
   - **发送端**（打开页面时一次性注入）：目标与形状、采集设备、声音（有 / 无 / **已弃**，
     就是 §1.5 那条"弃声保画面"）、编码器 + 目标高度 + `fps` + GOP、档位码率、
     **发送端队列秒数**与 DLNA 预填秒数（这两项就是 §1.6 里那份延迟预算，落在真正付它的那一格）。
   - **推流（每秒轮询）**：编码器产出的块数与字节、**发送端丢块**、已交付字节、观看端数、
     **重播等关键帧次数**（这一格只在非零时出现，见上面第 5 条）。
     「发送端丢块」是这一格里最有用的一条：卡顿如果是它涨，问题在**这个观看端读得太慢**，
     整块被丢了；它不涨而画面仍卡，问题在编码器或解码端。
   - **播放器（本机自己算）**：接收码率（1 秒滑窗）、已收字节与片数、MSE 追加积压、
     **距直播边缘**与已缓冲总长、**帧率报两个数**（`解码` 取自 `getVideoPlaybackQuality()`
     的每秒增量，`上屏` 取自 `requestVideoFrameCallback`）、掉帧、解码分辨率与画面元素尺寸、
     最近一片距今多少毫秒。两个帧率必须分开：**窗口被遮住或退到后台时，Chrome 只给这个窗口
     刷 1–2 fps，而解码端照常 24 fps** —— 只报上屏那一格就会把浏览器的节流读成"镜像坏了"，
     所以差得远时面板会自己写明「窗口不在前台，上屏数不算链路」。
   代价说清楚：**面板收起时一次请求都不发**（轮询只在展开期间跑），而且
   **这块浮层只有浏览器目标有** —— 投到 Chromecast / DLNA 电视时画面不在我们手里，
   那边要看这些数字仍然只能回到发送端设置页的「电脑投屏 → 统计信息」卡片。
   两处读的是**同一批计数器**（会话与分发器各一份，谁都不自己另算），所以不会出现
   "卡片说没丢块、浮层说丢了 30 块"。

**这条路验证到什么程度**：MSE 主路径与"中途接入"在**真机 + 真浏览器**上走过（本机采集
1920×1080，页面报「正在镜像」、`currentSrc` 是 `blob:`、缓冲稳定领先约 2–3 秒；
分帧修复后又从局域网**中途接入了一次实时流**，381140 字节走 ISO-BMFF 盒子遍历解析出
50 个 box、`ftyp`+`moov` 之后全是成对的 `moof`+`mdat`，零个游离字节）；
渐进式回退只在同一台机器上被动到过，**没有**在 Safari / 手机浏览器上系统验过。
统计浮层是 2026-09-24 在真浏览器（本机采集 1280×720、`currentSrc` 为 `blob:`、
`readyState=4`）上验的：展开/收起、刷新后按 `localStorage` 记住、收起时 6 秒 0 次请求
而展开时 6 次，都在页面上量过；浮层与 `/browser/stats` 的读数与发送端卡片逐格对得上。
**这一趟抓出两个只在真浏览器里现形的缺陷**：① 内嵌 JS 的 `'\n'` 被非 raw 的 Python 字符串
吃掉，页面抛 `SyntaxError` ⇒ 面板全空、按钮死、视频不播，而**当时 18 条 Python 用例全绿**
（现在 `PLAYER_PAGE` 是 raw 串，并有用例扫服务端真正吐出的那份 JS：任何 JS 字符串不许跨真实换行）；
② 档位码率那一格把**比特每秒**的档位喂给了按**字节每秒**算的格式化函数，4 Mbps 印成 32 Mbps
（现在两个单位各有格式化函数，用例绑住这两处）。
浮层**没有**在手机浏览器 / Safari 上验过，也没有在第二个观看端并发时验过（多观看端只有
打桩用例覆盖）。

**v0.19 那个数（每帧一片）也是在真浏览器里量的**（`scripts/mse_latency_probe.py`：
真采集 + 硬件编码 + 无头 Chromium 当观看端，从播放页自己的 `getVideoPlaybackQuality()`
与 `requestVideoFrameCallback` 读端到端 lag）。它对照的不是一个模型而是**同一棵树改动前的
那份代码**：同一个 `-g 12`、同一条采集与编码 argv，只把 `movflags` 从 `frag_keyframe`
换成 `frag_every_frame` ⇒ lag p50 1305 → 838 毫秒。同趟还量了"停在边缘后 0.5 秒"这一档
（829 毫秒，与 1 秒档差 9 毫秒）和 `-g 2`（画质 93.9 → 81.1，否掉）。**这一趟同时让
"v0.18 说分片节奏是 0.5 秒所以每帧一片买不到东西"那句话作废** —— 那条推理把分片粒度
当成了延迟的全部来源，而探针显示它正好是最贵的那一段（约 470 毫秒）。真机验收只做了
这一台机器 + 一个无头 Chromium；Safari / 手机 / 真电视一律没验，和上面浮层同一条边界。

**2026-10-02 之后，"跨机器"这一半不再是空的**：第一次真跨机验收是
**Windows（192.168.1.68，ddagrab 采集）→ Mac（本机浏览器当观看端）**，
browser/MSE 形状跑通了，并且这一趟把队列深度那个 28% 自丢量了出来（见 §1.6）。
同一趟还**证伪了我自己先前读出来的一个数**：那条链路一开始读起来像"媒体时钟只有墙钟的
0.80 倍"，实际用片内时间戳对墙钟重量是 **0.983–0.985、播放速度 1.00x** —— 0.80 是我
探针自己的墙钟计时假象（它把 HTTP 分块的到达间隔当成了媒体时长），不是 Windows 的锅。
**仍然没验的**：Safari / 手机浏览器、真无线链路（这一趟走的是有线局域网）、真电视。
两条形状的**端到端 lag 数字在 2026-10-03 都量过了**：本机一轮（WebRTC 369 毫秒对浏览器
492 毫秒，见 §1.4b 末），跨机一轮（WebRTC 400 毫秒；浏览器那一侧**量不出数字**，因为画面本身
被采集端饿住了 —— 见 §1.4b 末的跨机段与 `docs/research-screen-mirroring-transport-2026-10.md` §11）。
上面那个 838 毫秒是**另一支探针、另一段**，别和这两个数互换。

安全说明（为什么地址长这样）：镜像页地址里的 token 是**每会话随机**的，
故意不复用 Macast 的常驻管理令牌 —— 镜像 URL 会被复制、转发、贴进群，
而管理令牌泄露一次等于永久开放整套管理 API。地址请只发给愿意给他看屏幕的人。
统计浮层的数据来自同一个端口上的 `/browser/stats`，**用的是同一个页面 token、
同一道常量时间比对**（缺 token 或 token 错都是 403），而且页面正文里**不会再抄一遍
这个 token** —— 它由 JS 从自己所在的 URL 读回来。浮层所有文字都走 `textContent`，
永远不当标记解析。

DLNA/Chromecast 投屏推过来时会**让位**并转投该 URL（Bridge 行为）；
**浏览器目标下推送会被明确拒绝**，不会偷偷杀掉你的镜像。

### 1.4b 目标：浏览器 · WebRTC（低延迟 · 此通道无声音，v0.22）

§1.4 那条路的画面要经过一个 MSE 播放器；这一条干脆**不在链路里放播放器那一层缓冲**：
浏览器里开一个真正的 `RTCPeerConnection`，编码器吐出的 H.264 按访问单元切好、
**零重编码**装进 RTP 走 SRTP（发送端只做 NAL 拆分与打包），接收端自己的 jitter buffer
就是全部排队。

1. 「投屏方式」→ **浏览器 · WebRTC（低延迟 · 此通道无声音）**，点「开始镜像」。
2. 右栏「观看地址」出现 `http://<本机>:<端口>/webrtc?token=<每会话随机>`，
   复制到局域网里任何一台能开网页的设备（或点「在本机浏览器打开」）。
3. **这条通道没有声音**（标签里写着）：RTP 里只装视频。要声音用 §1.4 的浏览器目标
   或 §1.1 的 Chromecast。

**要装两个可选依赖**：`aiortc` 与 `av`。本仓库打包的产物已经带着它们；从源码跑时，
在**运行 Macast 的那个 Python** 里执行 `pip install aiortc av`（这两个包也点名在
`requirements/common.txt` 里），装完回到「投屏方式」重选本目标即可 —— **失败不会被缓存，
不需要重启 Macast**。没装就点「开始镜像」会当场失败，失败信息就是这行 pip。

- **不需要 ICE / STUN 服务器**：局域网里交换的就是 host candidate 本身；信令走 Macast
  自己的 HTTP（页面、换 offer、交 answer 三扇门），每扇**只认本次会话的 token** ——
  管理令牌不算、别的会话的 token 也不算。观看地址可以转发，但只该转给愿意让他看你屏幕的人。
- **最多 4 个观看端**，超了会点名拒绝而不是饿死已有观看端；半协商的观看端 30 秒回收；
  ICE 收集最多等 2 秒（host candidate 就是全部故事，这个上限是防 VPN 网卡把首绘扣住）。
- **`-g 12`（0.5 秒）在这一路上换了个含义**：接收侧没有编码器可以应答 PLI，所以
  丢包后的恢复、以及中途加入的观看端等第一张完整图，等的都是这 0.5 秒。
  它的队列同样按 0.5 秒的访问单元预算，满了丢整单元、等下一个关键帧 ——
  **新观看端在握手那一两秒里被丢掉若干单元是设计如此**（浏览器从 offer 到 SRTP 连通
  本来就要一两秒）。观看页与信令的请求**不计进**「一次会话的头几次交换」那几行日志
  （那几行留给媒体请求当证据）。
- 推流统计浮层与 §1.4 同款（顶栏「统计」，读的是同一批发送端计数器）。

**这条路验证到什么程度**：真浏览器两轮验收全 PASS（software x264 与 hardware
VideoToolbox 各一轮）：协商结果是 `video/H264`（不是 VP8 —— 那个静默协商 bug 有回归
用例钉着）、解码 24 fps / 上屏 23–25 fps、页面自己的帧计数器与外部探针互为双见证、
canvas 抓帧亮度非均匀（真画面不是全黑）、`live` 计数与发送端逐格一致、关闭浏览器后
观看端数回 0。端点检查脚本：`scripts/webrtc_page_probe.py`。
**边界**：跨机器这一半在 2026-10-02 补上了（Windows 192.168.1.68 采集、Mac 上的真浏览器观看，
画面真的在动），和 §1.4 同一条路；**Safari、手机、真无线链路仍未验**。

**端到端延迟量出来了（2026-10-03，本机）**：这一条目标是「低延迟」这个标签的承担者，
所以标签后面现在跟着数字 —— 屏幕到屏幕 **约 369 毫秒**，同一台机器、同一套测量、
同一次会话条件下，上面那条浏览器（MSE）通道是 **约 492 毫秒**。测量是一支闪光探针做的：
一个无边框窗口按墙钟时刻涂黑/涂白并把每一次时刻写进文件，观看页自己每帧采一次画面亮度、
配上 `Date.now()`，同一台机器同一个 epoch ⇒ 两个时钟之差就是整条链路（采集 → 编码 → 网络 →
播放器 → 合成）。三条读这些数字的人必须知道的限定：
① **参考时刻取在 AppKit 把窗口推给显示器之前**，所以每个数都**偏保守**，最多偏出一帧（约 42 毫秒）；
② 测量时旁边一直开着一扇小窗在闪 —— macOS 的采集是**按变化给的**，静止桌面上交给采集器的
每一帧都被钉成 1/24 秒的间隔，媒体时钟只剩墙钟的约 0.4 倍，不喂内容的话量到的每个延迟都会虚高
（这一条在不懂之前让同一支探针报出了 800–1500 毫秒的"浏览器延迟"）；
③ 两个数都**只在一次会话的新鲜阶段成立**：同一个浏览器页面在两十分钟的会话上只呈现出 17 次闪光里的
7 次，读数落在 800–1500 毫秒。**跨机那一段（Windows 采集 → Mac 观看）仍然是 0.98× 媒体时钟、
但没有用这支探针重量过延迟**。
这两个数与 §1.4 那个 838 毫秒**不是同一件事**：`scripts/mse_latency_probe.py` 读的是播放器的
缓冲边缘（`wall − buffered.end`），闪光量的是屏幕到屏幕。数字在代码里只有一处
（`MEASURED_LAG_MS`），两张卡片、帮助弹层与回归用例读的都是同一份。

**跨机那一段也量了（2026-10-03，Windows .68 采集 → Mac 浏览器观看，同一支闪光仪器）**：
WebRTC 在对面那台机器上是 **p50 400 毫秒（371–442，15 次闪光里 14 次对得上）**，编码换成
`h264_nvenc`、多了整整一跳，但**没有量出可见的代价**（本机 369 毫秒），所以「低延迟」这个标签
不需要跨机限定语。同一台机器、同一套仪器打浏览器（MSE）形状**量不出延迟**，原因是采集那一侧：
闪光窗排了 16 次翻转，页面只画出 10 次亮度穿越（另一次跑只画出 6 次、还有一次画面根本没起来），
而播放器自己一切正常（1.004× 速度、落后直播边缘 0.44 秒、`drops 0`、`misses 0`）——
**饿死的是画面，不是网络**。机制与十二路 A/B 在
`docs/research-screen-mirroring-transport-2026-10.md` §11，一句话版本写在 §1.5 的 Windows 那一行。
**因此这一路目前没有可报的跨机延迟数字，也请不要拿本机那两个数去推算一个**（推断值约 520 毫秒，
那是算术不是测量）。

### 1.5 系统声音（三个平台不一样，这不是我们的选择）

| 平台 | 状态 | 首次设置 |
|---|---|---|
| **macOS** | 13 及以上：ScreenCaptureKit 原生带进系统声音，**不用装任何东西**（v0.21）。更老的系统、或这台机器上 ScreenCaptureKit 不可用时回落 BlackHole 虚拟声卡（**FFmpeg 发行版至今抓不到 mac 系统音频**） | 13 及以上什么都不用做。老系统走页面「系统声音」→「一键设置」。它**先判断你的机器处在哪一格**（下表），再决定做什么：只有"真的没装"才下载官方 `.pkg` → **弹出图形安装器，你输一次密码**（`.pkg` 无法静默安装，别期待全自动）→ 等设备出现 → 建/复用名为 `Macast Screen Mirror` 的多输出聚合设备 → 把默认输出切过去。**面板里那 11 步行是实时推进的**（跳过的行不进分母，进度条永不回退），也可以点「打开详细进度页」在浏览器里看同一份进度。**任何一步失败就降级**：打开「音频 MIDI 设置」+ 文字指引。装完这一行会出现「恢复原声音输出」按钮，走它回去 |
| **Linux** | PulseAudio 直接有 tap | 采集口是 `<sink>.monitor`，插件自动探测；Wayland 下**没有画面可采**（x11grab  only），会明说 |
| **Windows** | 需要一块**回环录音设备**（ffmpeg 的 dshow 输入只能读系统认成「输入」的东西） | 插件自己探 dshow 设备表，认出携带输出的那块（驱动自带的「立体声混音 / Stereo Mix」，或你装的虚拟声卡 VB-Cable / VoiceMeeter 等）就直接用它，**不需要任何设置**。**但这个开关有实测到的代价**（2026-10-03 在真机上量，`docs/research-screen-mirroring-transport-2026-10.md` §11）：把这块设备**读进输出**会让**画面本身**从 24 fps 掉到每秒约 1.5 次内容变化 —— 字节照发、播放器不报错、声音也真的进得来，缺的是新鲜度，而「浏览器」观看页是最看得见这一格的地方。同一个采集口**只打开不读**（WebRTC / Chromecast 低延迟这两条按构造就是这么做的，它们也因此没有声音）画面就是完整的 24 fps。所以：**要画面就跟目标选「浏览器 · WebRTC」，或去 Windows 的声音设置里禁用那块回环设备**（禁用后插件探不到，就只采画面 —— 那是你的机器设置，插件不会替你动，也没有页面开关）。十二路 A/B 试遍了对侧：缓冲大小、线程队列、去掉我们的重采样、交错上限、换容器 —— **全都没买回来**，而且这个 ffmpeg 发行版没有 `wasapi` 输入。没有这种设备时仍然只采画面，但「系统声音」那一行会告诉你**去哪开**：`设置 → 系统 → 声音 → 更多声音设置 → 录制`，右键空白处勾上「显示已禁用的设备」再启用「立体声混音」；驱动没提供就装一块虚拟声卡，然后点「重新探测采集」 |

> **Windows 声音在真机上量过**（2026-09-23，AMD-YES / Windows 11 / ffmpeg 8.1.2）：
> 那台机器的 dshow 表里有「立体声混音 (Realtek(R) Audio)」，直接采集 6 秒得到
> `pcm_s16le 44100 Hz stereo`、`n_samples: 573300`、`max_volume: -22.9 dB` —— 开得起来、
> 送的是真采样、不是数字静音。（注意设备给的是 44.1 kHz，插件强制 `-ar 48000` +
> `aresample=async=1` 处理这个重采样。）**之前没有声音不是硬件不支持，是插件把 Windows
> 分支写成了 `-an`。** 另外，`gdigrab` 在非交互会话（例如 SSH 登录）里会报
> `Failed to capture image (error 5)` —— 那是那条通道没有桌面可抓，不是插件的状态；
> 在交互桌面里启动的 Macast 画面正常。

### 1.5b DLNA 电视找不到设备：多网卡要逐个试（Windows 上尤其）

「找不到 DLNA 设备」与「发现包根本没发出去」在页面上长得一模一样，所以两件事都要能看出来。

- **只从一块网卡发一次 M-SEARCH 是不够的。** 插件原来只发一次「交给内核路由」的发现包。
  实测（同一台 Windows 11 机器，10 个 IPv4）：**内核路由的那一次拿到 0 个应答**；分别绑定后
  `192.168.1.68` 拿到 2 个（`192.168.1.13` 电视 + 本机 Macast），而 Tailscale（100.122.246.80）、
  Hyper-V（172.23.48.1）、链路本地（169.254.x）各 0 个。装过 Hyper-V / WSL / Docker / VPN 的
  Windows 机器普遍有这种网卡，**组播出口未必是你以为的那一块**。
- 现在：**空结果才回退**，按可广播地址逐个重发（最多 4 个），任何一个有应答就立刻停 ——
  单网卡机器一分钱不花。每次都记进「统计信息」的 `发现尝试 · <网卡>` 行，页面上也能看到。
- 全部尝试都**发不出去**（而不是没人应答）时，仍然报「DLNA 搜索发不出去」—— 这两种情况
  该做的事完全不同，不能合并成一句「没有发现」。

**五种机器状态、五种做法**（v0.9）。**先说适用范围：这张表是回落到 BlackHole 那条路的事**（macOS 13 以下，或这台机器上 ScreenCaptureKit 不可用）；13 及以上的原生采集不经过任何音频设备，也就没有"装什么、重载什么"这回事。之前它把"驱动文件在磁盘上"这种情况**写在提示里说会跳过安装，
然后照样重新下载一次安装器** —— 于是出现「装了却没有设备 → 再点又装一遍 → 永远装不完」。
现在"跳过"是流程里真正的跳过，不是文案：

| 你的机器 | 怎么判出来的 | 一键设置做什么 |
|---|---|---|
| 能采集系统声音 | ffmpeg 的采集设备表里有 BlackHole | 什么都不装，只把多输出设备建好/复用 |
| 驱动已加载，但采集看不到 | CoreAudio 有、ffmpeg 没有 | **不重装也不重载**（两者都改变不了这件事）：照样把聚合设备建好，然后指名去「系统设置 → 隐私与安全性 → 麦克风」给 Macast 授权，重启 Macast 再点一次。旧产物（v0.9 之前打包的 `.app`）没声明麦克风用途，系统连授权弹窗都不会给 |
| 驱动在磁盘上，但音频服务没加载 | `/Library/Audio/Plug-Ins/HAL/BlackHole*.driver` 在、设备表里没有 | **跳过下载与安装**，只要一次管理员密码**重载音频服务**（官方 `.pkg` 的 postinstall 只改权限、从不重启 coreaudiod。**不需要重启电脑**，重启只是等价手段） |
| 只有残留的安装记录 | pkgutil 有记录、文件不在 | 重新下载官方 `.pkg` —— 这就是"上次装了却没有设备"的原因 |
| 什么都没装过 | —— | 完整走一遍：下载 → 校验 sha256 → 安装器 → 等设备安装 → 重载 → 建聚合设备 |

**每一格都保证同一件事：再点一次不会重新下载已经装好的东西。**

**「已启用」与「有声音进来」是两件事**（2026-09-23）。BlackHole 是一根线，不是一个分线器：
它传导的是**被送进它**的声音，也就是默认输出必须是那个多输出聚合设备（或你自己做的等价物）。
装了、也选了，但默认输出还留在扬声器 ⇒ 采集口一切正常，镜像里就是静音 —— 而页面以前只写
「系统声音：已启用」，看起来像编码器的锅。现在那一行会做两次提问：ffmpeg 能不能采这个设备
（`_capture_cache` 的探测结果），以及这台机器自己的默认输出到底是谁（`system_audio_routed()`）。
后者答不上来时（某些沙箱里逐设备的 CoreAudio 读被拒）它说"不知道"，而不是猜一个绿色。

也要说清楚没做到的部分：聚合设备的**属性字典键**在这台机器上无法核对（命令行工具沙箱里
只有默认输出读得到，逐设备读一律 `!dat`；CLT 的 SDK 里没有 `AutoHAGTypes.h`，也没有可参照的
键名字符串）。所以我们**没有**改 `_create_aggregate` 的那套键，只把"看得见的那一半"变成读数 ——
与其按一个没验证过的规格改代码，不如如实报"声音有没有路由进去"。

**13 及以上的 ScreenCaptureKit 不走这根线**（v0.21）：它的音频 tap 直接读系统混音，默认输出是谁都听得到，所以上面那套"路由判定"不适用于它（页面也不会拿默认输出当头问）。代价是另一种边界：SCK 的声音与画面共用一次会话，它没能送来声音时被动刀的是这一路音频，而不是某台设备 —— 形状见下条。

**读不到的音频口会连画面一起饿死，而且一声不吭**（2026-09-23 在装好的 `.app` 上实测；这是 avfoundation 回落路径上的形状）。
avfoundation 把系统声音当作**输入**设备，所以它吃的是**麦克风**授权，不是屏幕录制；授权没给到
（或 BlackHole 那头没人喂时钟）时，ffmpeg 不报错，而是**一帧画面也不给**。以前这一格只会被
翻译成「屏幕采集在 3 秒内没有返回画面」+ 两行 ffmpeg 的运行时噪声（`objc[…]: class … not linked
into application` 和 `Configuration of video device failed, falling back to default.`）
—— 而这两句在**正常采集里也会出现**，把它们当原因只会把人带偏。现在的行为：

- 3 秒内拿不到帧、而且这一轮带着音频口 ⇒ **先去掉音频口重起一次采集**。画面能起来，镜像就继续，
  通知会明说「本次镜像没有系统声音」并点名麦克风那一格与「勾选后重启 Macast」；
- 这件事**不只活在那一次通知里**：页面上「系统声音」那一行原来只回答"机器配置成什么"，
  口探得到、默认输出也路由过去了，这一次镜像里却可以什么都没有。现在它先问会话自己 ——
  弃了声就直说"这一次镜像没有声音"并给出那道门，状态行也带上「本次无系统声音」；
- 去掉音频口还是没有帧 ⇒ 这才是真的采不到，失败文案只留 ffmpeg 输出里**不是运行时噪声**的那几行，
  并且一定给出「系统设置 → 隐私与安全性 → 屏幕录制」+ 重启（改动只对新启动的进程生效，
  而 ffmpeg 是我们 spawn 的子进程）；
- 那两句噪声照旧写进 `logs/ScreenMirror.log`（排障要看得到），只是不再冒充消息。

**v0.21 起 macOS 13+ 走 ScreenCaptureKit，弃声是另一种形状**：SCK 的音频即使无声也按 20 毫秒的节奏送整幅零 PCM（所以它不会像"静默管道"那样把整条命令冻住），但只要它**一直没送来**系统音频（2 秒宽限），这次镜像就**先去掉声音继续** —— 页面「系统声音」那一行会立刻写明原因与「重启 Macast 再试」，之后的镜像连开始通知也会带上这句，而且本次运行里之后的镜像都先跳过声音（要再试一次，**重启 Macast** 才会重新等它）。去掉声音的方式是关掉编码器的音频写端，不是把采集重起一遍。

镜像期间持有 `caffeinate -dimsu` 休眠断言（合盖/息屏会把镜像打断），停止时释放。

### 1.6 画质、编码器与延迟预算（2026-09-23 起这些是一个算出来的数，不是四个手感值）

用户报的三件事 —— 「延迟大」「有杂音」「不开硬件编码几乎看不见」—— 都落在同一处代码里，
所以放在一起说。

**四档画质**（`QUALITIES` / `QUALITY_LABELS`，帧率固定 24 fps）：

| 档 | 高度 | 视频码率 |
|---|---|---|
| 360p · 2 Mbps（省带宽） | 360 | 2 000 000 |
| 720p · 4 Mbps（默认） | 720 | 4 000 000 |
| 1080p · 6 Mbps（更吃带宽） | 1080 | 6 000 000 |
| 原始分辨率 · 8 Mbps（不缩放） | 不缩放 | 8 000 000 |

再往上就没有意义了：桌面不是胶片，一帧大体静止的画面值不了 16 Mbps，而那 16 Mbps
买到的是**排队的字节**——队列满了就丢一块，丢的那一块里有音频，于是**卡顿是听得见的**。
每一档另外带一个 VBV 上限（`-maxrate` = 1.5×，`-bufsize` = 1× 码率）：没有上限时，
一次拖窗口、一次终端滚屏会被编码器按它想多大就多大吐出来，那一帧恰好就是撑爆队列的那一帧。

**发送端自己那份延迟**：一个预算（`LIVE_QUEUE_SECONDS` = 0.75 秒），**三种单位**
（`live_queue_units()`），因为三种容器各自"排队的最小块"不一样：

- **不分帧的 MPEG-TS / PS**（Chromecast、DLNA 直播）：排的是 4 KiB 的读块，
  所以 0.75 秒换算成块数后夹在 64–256 之间（`live_queue_chunks`）。720p 那档就是
  0.75 秒，最低档被 64 块的下限托到约 1.05 秒。以前的 256 块是个固定的**字节**数，
  在 2 Mbps 下约等于 4.2 秒的积压。
- **分片 MP4（浏览器目标）**：排的是**整个片段**，所以秒数必须除以"一秒有几个片段"
  —— 而 `frag_every_frame` 是**按 sample** 的节奏，不是按画面：音频在同一次 flush 里
  复用，24 fps 带系统声音时线上一秒写 **24 + 46.875 ≈ 70.9 个 `moof`**
  （2026-10-02 在真会话上量的：15.02 秒 1063 片 = 70.8 片/秒，平均每片 8,835 字节，
  和算术对得上）。**v0.23 之前这里按 `fps` 甚至按一个写死的 8 报价**，于是 0.75 秒的
  预算落成真容量 **8 个片段 = 0.11 秒**，慢一点的消费者会**自己把自己丢掉的帧读成卡顿**
  —— 那一轮量到的是 **28% 的自丢**。现在这一档是 **54 个片段**。
- **直播 Matroska**（DLNA 里必须从头读的档位）：排的是整个 Cluster，而封装器按**大小**
  闭合它（实测 50–60 KB），所以秒数对着 `MKV_CLUSTER_BYTES` 花。

队列的**单位**和分发器分片的**依据**（`init_marker`）读的是同一个值，二者必须一起决定。
**WebRTC 目标不在这三行里**：它的队列按 0.5 秒的访问单元报价（12 个），满了丢整单元
并等下一个关键帧 —— 那里丢的从来不是字节块。电视/浏览器自己那一段不在这里，
也不被我们声称量过。

**丢字节的单位**（这是"杂音"的第一处根因）：

- 浏览器目标按**整个片段**丢（见 §1.4）：v0.19 之前一个片段是一个 GOP（0.5 秒），
  首帧就得等那么久才发得出；现在分片是每帧一片，这个等待 ≈ 41.7 毫秒。
  `-g 12` 保留 —— 但它现在管的是**恢复粒度**（每隔多久有一个可作重播起点的关键帧），
  不再是发布节奏。
- Chromecast / DLNA 目标是 MPEG-TS / PS，丢块必须落在 **188 字节包**的边界上
  （`_Broadcaster(packet_align=188)`）。在包里切断，接收端重同步时那个音频帧就少了中间，
  听出来是一声爆音而不是画面跳一下。编码器吐出的最后半包在 EOF 时照样交出去，
  不被扣在对齐器里。
- 虚拟声卡的时钟与屏幕采集的时钟不是同一个晶振，漂一点就要在输出侧重采样校正
  （`-af aresample=async=1`）。第三处根因是 BlackHole 装了但系统声音没路由到它 —— 那一条
  现在会写在「系统声音」那一行里（见 §1.5）。

**编码器**：「自动」（默认）/「软件编码（x264）」/ 一条**按平台改名**的硬件档
（macOS 上是「VideoToolbox 硬件编码」，Windows 上是「NVENC 硬件编码」）。
这不是装饰：`HARDWARE_ENCODERS` 是一张平台表（darwin → `h264_videotoolbox`，
win32 → `h264_nvenc`），Linux 故意不在表里，所以那一行在非 macOS 平台上问的从来
不是"有没有 VideoToolbox"，而是"这台机器的硬件编码器能不能真的开起来"。
**默认值现在是"自动 = 一旦探过就用硬件"**。这句话的理由在 2026-10 被换过一次，
两半都留在文档里：2026-09-23 所有者报的"不开硬件几乎看不到画面"**是真的**，
但根因不是"软件编码器追不上采集" —— 实测里 x264 `ultrafast`+`zerolatency` 喂
**真实 24 fps 桌面采集**在 1080p 只吃 **0.59 个核**，VideoToolbox **0.41 个核**
（`scripts/encoder_latency_probe.py`，三次跑；之前那些"每秒几百帧"的数喂的是**文件**，
是离线吞吐天花板，不是镜像的成本）。真正的两条成因都是**零字节产出**的编码参数 bug
（原画高度被写死的 `-level 42` 拒掉；软件路径漏钉输出 `-r` 时 x264 算出荒谬的 MB rate
而一个字节都不编），已各自修好并有回归用例。所以今天这笔账是
**首帧约 200 毫秒 换 0.18 个核** —— 翻不翻这个默认是用户的决定而不是测量结果，
所以页面把账说出来（`ENCODER_TRADEOFF` 进「采集」卡那条 hint，并注明两边都含约 0.5 秒
ffmpeg 启动、要看差值）。两个约束值得知道：

- 探测要 spawn 一次 ffmpeg，而这条问答题出现在菜单与页面的构建路径上，
  所以**代码绝不为它 spawn**：没探过就按软件走，探过的答案按 (ffmpeg 路径, 平台) 缓存。
  一次镜像启动、或跑一次 `scripts/selfcheck.py`，就会把缓存填上，之后自动档直接给硬件。
  **两个平台的探测形状不同，因为它们的失败模式不同**：macOS 问 `ffmpeg -encoders`
  的清单就够了（VideoToolbox 是操作系统框架，不是驱动 —— 清单里有就说明系统里有）；
  Windows 必须**真的编半秒测试图**（`_encoder_opens()`），因为那台 2026-10-02 量过的机器上
  清单同时列了 `h264_nvenc` / `h264_qsv` / `h264_amf` 三个，而 `h264_qsv` 连会话都开不起来
  （`Error creating a MFX session: -9`、零字节、非零退出）—— 清单说的是"符号在二进制里"，
  不说"驱动在机器上"。所以 Windows 的硬件档只可能是**编出来过**的那一个，qsv 与 amf
  是被量着排除的，不是被猜排除的。
- 显式选了「硬件编码」而机器其实没有，不会当场失败：启动时回落 x264 并在日志里说清。

**码率承诺**（"为什么线上码率和档位数字对得上/对不上"）：`rate_target()` 只对
VideoToolbox 乘 1.5 —— 因为**只有它少给**（要 4 Mbps 实发 2802 kbit，是保守不是画质差；
同一个 4 Mbps 目标下 VT 的 VMAF 91.47 还高于 x264 ultrafast+zerolatency 的 90.78@4216 kbit）。
x264 与 **nvenc 都被要求落在档位数字上**，nvenc 是量过的：档位 6000 kbit 时线上实测
6052 / 6081 / 6087 / 6029。**所以"码率明显低于档位"这句话现在只在一种情况下是警报**：
你选的是软件档或显式硬件档、而那个编码器其实没被启用（回落发生在启动时、不在判断时）。

**关键帧间隔（`-g`）**：三个数，各自属于各自的链路，别混。

| 目标 | `-g` | 为什么是这个数 |
|---|---|---|
| 浏览器（fMP4） | `FPS // 2`（12 帧 = 0.5 秒） | v0.19 起分片跟着每一帧走，发布节奏不再由它决定；这个数现在买的是**恢复粒度** —— 重播割点最多要往回退这么远才遇到一个可播的画面 |
| WebRTC（浏览器直连） | `FPS // 2`（12 帧 = 0.5 秒） | 接收侧没有编码器可以应答 PLI：丢包后的恢复、以及中途加入等第一张完整图，等的都是这 0.5 秒；它的访问单元队列也按这个数报价 |
| Chromecast / 低延迟通道 | `FPS`（1 秒） | TS 不按关键帧分片，这个数只是恢复粒度，1 秒付得起 |
| DLNA 直播档位（H.264 两档） | `live_gop()` = **0.25 秒**（25 fps 下 6 帧） | 2026-09-23 从 1 秒改到这里 |
| DLNA 的 MPEG-2 三档 | `fps * 3 // 5`（0.6 秒，在 `_mpeg2` 里） | DVD 时代解码器的经验值，**没有**为它做过测量，也没动它 |

DLNA 那一行为什么值得改：电视是**随时加入**的观看端，两个机制都卡在关键帧上——
Matroska 在下一个关键帧才闭合 Cluster，没闭合的 Cluster 发不出去，于是 `mkv-h264` 上
GOP **就是**发布节奏；而探测窗口越过开头 IDR 的解封装器要等下一个 IDR，最多等一个 GOP。
本机对自己那台接收端量到的首帧（同一档位、同一台机器、跑两次）：

- `mkv-h264` 硬件编码：`-g 25` → 3.31 / 3.26 秒；`-g 6` → 2.47 / 2.44 秒。
- `ts-h264` 软件编码：`-g 25` → 2.97 / 2.97 / 2.97 秒；`-g 6` → 2.50 / 2.49 / 2.50 秒。
- `ts-h264` 硬件编码：2.05 / 2.05 对 2.04 / 2.05 —— **没差别**，硬件编码器快到在探测结束前
  画面就已经在屏幕上了。也就是说这一改的收益集中在"慢的那一档"，不是普遍的一秒。

代价是带宽不是画质：高运动测试片上 x264 涨 6%（6.61 → 7.02 Mbps）、VideoToolbox 涨 9%
（5.66 → 6.19 Mbps），而 SSIM 在小数点后第四位是平的（0.9983 对 0.9982、0.9985 对 0.9986）——
四倍的关键帧，画面看不出来。稳定落后在这些跑动里一格没动：**这一改买回来的是首帧，
不是运行中的延迟**。低延迟 Cast Streaming 通道另有自己的 `min_keyint`，不受这些常量管。

**封装的延迟**：TS 与 MKV 档位带 `-muxdelay 0 -muxpreload 0`（直播管道不该为交错再等一次），
而 MPEG-PS（`vob`）**不带**这一对 —— 实测这台 ffmpeg 上 PS 会因此自己的 VRV 缓冲下溢、
每条流都告警。这一对不省下的那半秒也确实量过：给 vob 加 `-preload 0` 会把
`start_time` 从 0.534667 压到 0.034667，直播首帧 5.86 → 5.30 秒，
但**没有随包发布**：PS 的 VRV 模型本来就靠这段交错余量活着，用下溢告警和花屏换 0.5 秒不值得。
真正的 3 秒差在容器本身，见 §1.3 那张表（`ts-h264` 1.9 秒 vs `ps-pal` 5.1 秒）。
这些数字改一处就要改文档与用例，Part 37 就是照着代码里的常量核对它们的。

**一次镜像的最大时长**（`Mirror_Max_Duration`，v0.24 起，在「画质」卡里）：三档 **12 / 24 / 48**，
默认 12。**故意没有「不限」这一档** —— 这一页的默认值从来没人去动，而"没人动就等于不设限"
正是这个旋钮要结束的那个状态；想更久就选 48，而不是把一个开关留在"无限"上。
读设置时越界或读不懂的值回落到默认（**不是拒绝**：一份改坏的 `macast_setting.json`
不该在半天后把一场演示拦腰截断，而那时没有人说得清为什么）。

只管两条**电视**通道（`MAX_DURATION_TARGETS = ('cast', 'dlna')`）。浏览器页、
Cast Streaming 低延迟、WebRTC 三条**永远不接 `-t`**，理由是形状本身决定的：那三个是
**直播边缘**的消费端，截断它们省不下任何编码开销（观看端刷新一下、重连一次就回到当下），
代价却是把一个正在讲话的人切掉 —— 电视则相反，它拿到的是一个"文件"或一条 LOAD，
多播一小时就多一小时的东西留在场上。

一个数只问一次：`bound_video_seconds()` 是唯一的真相点，ffmpeg 的 `-t` 和 DLNA
「伪装成文件」那对 `size=` / `duration=` 都从它算出来。**这条不是纯洁癖**：两个数不一致时，
电视会拿着一个我们永远发不出的长度去文件尾找不存在的索引（§1.3 那一条），
症状长得像"这台电视不认我们的流"。天花板对那一对**只许缩短**，而它在出厂档位上一次也没
缩短过：`DLNA_MAX_ADVERTISED_SIZE = 1.9 GB`（老固件把 `Content-Length` 当有符号 32 位整数）
先把长度卡在 **41–54 分钟**，五档全这样（逐档量过；`advertised_file()` 的 docstring 里
留着这句话）。所以它是给"哪天有人把档位码率调小"准备的保险，**不是今天生效的规则**。

到点是**主动停止并弹一条点名这个旋钮的通知**，不是悄悄把画面截掉：`_duration_expired()`
走正常收尾（`_teardown()` 而不是 `_fail()` —— 没有任何东西出错，编码器正好写完它被要求
的那幅画面，不该在日志里留一条 ERROR），同时释放"镜像期间不许休眠"的断言。
不做这件事的话，无人看管的镜像会一直编码到天亮。

**两个入口，一个结果**：我们的计时器是权威，ffmpeg 自己的 `-t` 是兜底，**哪个先到是时序
问题**（DLNA 的预填 + LOAD 往返有时让 `-t` 先落）。`_encoder_died` 从**已发布的诊断**里
把 `max_seconds` 读回来（不是再去读一次设置）认出"`-t` 到点"这一种死法，所以它不会被误报成
「屏幕采集中断」；generation 判定让这两个入口幂等，晚到的那一个闭嘴，用户只听到一次。
「统计信息」卡的「最大时长」行同样读 argv 里的 `-t` —— 卡片说的就是那条流水线被要求做的事；
而**不受约束的目标根本不会出现这一组档位按钮**（一个调不动东西的控件是句谎话）。

### 1.6b Windows 的画面采集：Desktop Duplication（ddagrab，v0.20）

Windows 上原先用 gdigrab，它抓的是**整块虚拟桌面** —— 多显示器时那是一整张画布：本机实测
gdigrab 在这台机器上报 **4000×2571**，奇数高度让 x264 直接拒绝
（`height not divisible by 2 (4000x2571)`），于是**「原始分辨率」档在这类机器上产出零字节**。
现在优先走 ffmpeg 的 `ddagrab`（DXGI Desktop Duplication，与游戏采集用的
Windows.Graphics.Capture 是同一套底层）：**每块屏幕按自己的尺寸采**，「采集」卡片里的
显示器列表就是这台机器真实的 DXGI 输出列表（v0.20 起 Windows 才有这个选择器）。

被桌面拒绝时（驱动不提供 Desktop Duplication、RDP 会话等），本次运行自动回落到 gdigrab，
原因写进插件日志（设置页「日志」→ 选 `ScreenMirror`），**同一次运行内不会反复重试
ddagrab** —— 每次重试都要白等一轮首帧预算，而拒绝通常不会自己变好。

**这条路验证到什么程度**（2026-10-02，Windows 11 build 26300 / ffmpeg 8.1.2，与 §1.5
声音验收同一台机器）：输出 0 与 1 各报 2560×1440 附着成功；第三块输出被逐字拒绝
（`Failed to enumerate DXGI output 2`）且探询就此停下。按出货 argv 跑 4 秒的浏览器形状
产出一个 4,176,319 字节的 MP4 —— ffprobe 报 h264 Constrained Baseline、2560×1440、
r_frame_rate 24/1、93 帧 / 4.021 秒，加 AAC 音轨，本地完整解码零报错。**没有验证的**：
Windows 镜像投到真电视 / 真 Chromecast、以及多显示器时选副屏的实际投出。

## 2. Local File Caster —— 把这台电脑磁盘上的文件投到电视

菜单栏切到 `Local File Caster`（与 Screen Mirror 互斥）。

```

<状态行：文件名 · 直通/转码/直投网址/系统声音 · 3/12 · 00:41/01:32>
播放控制 ▸   暂停/继续 · 下一个 · 上一个 · 停止（让电视回主页）
输出目标 ▸   Chromecast / Google TV | DLNA 电视 + 设备列表
媒体文件夹 ▸ 选择文件夹… → 文件列表 →「全部按顺序播」
```

**最常用的一条路**：输出目标选一台设备 →「媒体文件夹 → 选择文件夹…」→
点一个文件。就这么多了。

### 2.1 「自动」在做什么，为什么值得信

每个文件先过 **ffprobe**，决定两件事之一：

- **直通**（copy）：电视能自己解码 ⇒ 用一个内置的 Range/206 HTTP 服务
  **按字节**供原文件。电视自己的暂停/seek/音量全都作用在真实文件上，我们什么都不做。
- **转码**（convert）：AVI/MKV/HEVC/DTS/AC-3、你手挑的第二条音轨、内嵌字幕
  ⇒ ffmpeg 边播边转成 MPEG-TS。实现上写的是一个**会增长的文件**并由 HTTP 供它的字节区间
  （不是管道 —— 管道没有长度，DLNA 渲染器对没长度的流直接拒播），
  读取方跑得太快会**等编码器**而不是拿到短答。**seek 会从新位置重启编码器**，
  这是"转码进行中"能做到的诚实上限。

菜单底部那一行会写明这次是哪条路和原因（`直通：…` / `转码中：…，电视吃不下`）。
出问题时的第一判据就是这行；「处理方式 → 强制直通/强制转码」是用来对照验证它的。

转码会占临时目录空间（菜单里报出路径与上限，"结束即删"）；空间不够就回落到
"降码率以适配被 2 GiB 上限卡住的长度" —— 宁可画质下来，也不让进度条说谎。

### 2.2 音轨 / 字幕 / 同步，以及它们的边界

- **音轨选择与 A/V 偏移只在转码路径上有效**。直通是把原始字节交出去，
  电视的轨道列表没法从这里重排 —— 所以一旦你手挑了非默认音轨，
  决策函数就会把这个文件改派给 ffmpeg，菜单也是这么写的。
- **字幕三条路**，因为目标确实不同：Chromecast 把内嵌字幕转成 WebVTT
  并写进 LOAD 的 `textTracks`（由接收端画）；转码路径在**这台机器的 ffmpeg 带 libass**
  时烧进画面；**DLNA 渲染器两条都没有**。
- **停止发的是 `QUIT_APP`，不只是 STOP**。裸 STOP 会把接收端 App 停在最后一帧，
  这就是"我停了投屏但电视还卡着我的画面"这类 bug 报告的来源。
- **看门狗**（就是 mkchromecast 的 `--hijack` 那个想法）：每隔几秒问设备在干什么，
  我们的 app/URI 不见了就从中断位置重投，重试预算有限并且会认输 ——
  **手机想看电视就把电视让给它**。设备上报"播完了"，播放列表自动前进。

### 2.3 只投系统声音

勾选后不投画面，只把这台机器的系统声音做成音频档推过去。
采集口与 §1.5 同一套（macOS 需 BlackHole、Linux pulse monitor、Windows 没有）。
目标设备不支持时会提示「只有声音；目标设备不支持时请先关掉头选」。

## 3. AirPlay Screen Mirror —— 让 iPhone 把屏幕镜像**进来**

协议类插件（`<macast.protocol>`），与任意渲染器共存。它**不实现** AirPlay 镜像，
而是监督 **uxplay**（配对、stream key、AES-128-CTR 数据通道、GStreamer 解码都归它）。

**硬前置：这台机器上没有现成的 uxplay。** Homebrew 没有 formula，上游 release 里
也没有 macOS 二进制 —— 必须自己编译：

```shell
sudo xcode-select --install                       # 1) 命令行工具
brew install cmake libplist openssl@3             # 2) 依赖
# 3) GStreamer 去 https://gstreamer.freedesktop.org/download/ 装，
#    runtime 和 -devel 两个 .pkg 都要（落在 /Library/Frameworks/GStreamer.framework）。
#    别和 Homebrew / MacPorts 的 GStreamer 混用。
git clone https://github.com/FDH2/UxPlay && cd UxPlay
cmake . && make && sudo make install              # 4) 装
```

装完在「插件」页启用 `AirPlay Screen Mirror`，插件会用它自己的名字（= Macast 的
友好名） advertise `_airplay._tcp`，iPhone 的屏幕镜像列表里就能看见。

要知道的三件事：

- **别和内置 AirPlay 协议同时开**：手机会列出两个名字几乎一样的接收端，插件启动时
  会提示一次。**也别和 `AirPlay Audio (RAOP)` 同时开** —— uxplay 本身就是个完整
  AirPlay 接收端（自带横幅写着 mirroring and audio-streaming），
  它和 shairport-sync 会广播同一个名字，结果只有一个应答。
- **选项写在 Macast 自己的配置目录里**（`-rc <file>`），绝不碰 `~/.uxplayrc`
  （那是用户手写的文件）；用 `-rc` 而不是 `$UXPLAYRC`，因为后者指向不存在的文件时
  uxplay 会**静默回落**到 `~/.uxplayrc`，写失败就表现为"我的设置没生效"。
- **不加 `-p`**：那是 legacy 端口集，含 TCP 7000 —— Macast 自己的 AirPlay 协议要用的端口。
- 一期是 uxplay **自己开一个窗口**放画面；不映射成 DLNA 播放状态
  （镜像会话里没有 URL 也没有进度，连接/断开以通知形式报）。
- **验证状态：真 iPhone → 真 Mac 没测过，这台机器上根本没有 uxplay。**
  打桩测试覆盖的是：找不到二进制的正常路径、选项文件内容、四类事件各且只通知一次、
  意外退出时把 uxplay 最后几行 error 带出来、reload 与 stop。
- Apple 随时可能砍掉 Legacy AirPlay —— 届时这一条会**静默失效**，不是我们的代码坏了。

## 4. AirPlay Audio (RAOP) —— 让 iPhone 把声音推到这台电脑

同样是监督型协议插件，外部程序是 **shairport-sync**：

```shell
brew install shairport-sync        # macOS/Linux；Linux 上也可 apt install
```

启用后插件生成一份**最小配置**（只有 `general = { name = ... }`）并拉起它，
上报连接/断开。输出后端、混音器、端口都是你那台机器的系统决定，
插件故意不猜 —— 猜了就会破坏已经能用的配置。`uses_ssdp = False`。
与 `AirPlay Screen Mirror` 的冲突见上一条。

## 5. 出问题先看哪里

```shell
# 环境自检：依赖、端口占用者、可广播网卡、mpv、代理变量、在线索引三问，
# 以及下面这一整段发送端前置
env -u PYTHONPATH .venv/bin/python scripts/selfcheck.py

# 在线索引到底能不能装（退出码 0/2/3，可进 cron/CI）
env -u PYTHONPATH .venv/bin/python scripts/check_index_reachability.py
```

`selfcheck.py` 的「sender plugins」段逐项回答这几个问题：

| 它问什么 | 为什么值得问 |
|---|---|
| ffprobe 在不在 | 没有它，本地文件投屏无法判断"直通还是转码" |
| `-encoders` 里有没有 `libx264` / `h264_videotoolbox` / `mpeg2video` / `ac3` | **各对应一条会静默失效的链路**：前两个是镜像，后两个是老电视的 MPEG-PS 档位 |
| 有没有 libass（`subtitles` 滤镜） | 没有就只能走 WebVTT 字幕，烧字幕那条路不可用 |
| avfoundation 列没列出屏幕 | 没列出 = 屏幕录制权限没给。（v0.8 之前这一条**在真机上永远答"没有"** —— 是解析器读不懂 ffmpeg 的输出，不是机器没屏幕） |
| 系统音频采集口 | macOS **13 及以上先问两件事**（v0.21）：系统版本，以及这个 Python 环境有没有 ScreenCaptureKit 绑定 —— 都有就是「原生带系统声音，不用装任何东西」；缺绑定、或系统更老，才继续原来的两问：glob `/Library/Audio/Plug-Ins/HAL/BlackHole*.driver`，**再问 ffmpeg 列不列得出它** —— 文件在盘上但 coreaudiod 没加载 = warn（v0.9 之前这里会说 ok，而插件说没有采集口，两边看起来像互相打脸）；Linux 问 `pactl` 要 sink monitor；Windows 直接说"仅画面" |
| 转码临时目录剩余空间 | 转码写的是"会增长的文件"，空间在半路用尽比开头就报更难查 |
| 局域网里有没有东西可投 | 真发一次 mDNS browse（`_googlecast._tcp` / `_airplay._tcp`）和一次 SSDP `MediaRenderer` 探测。**没搜到电视的时候，「设备」卡片里空空如也就不是插件的问题** |

这一段是**只读**的：它直接读 `macast_setting.json` 的文本，不经过 `Setting`，
所以跑自检不会改你的配置。回归用例 **Part 32** 守着它和两个插件说的是同一套话
（编码器集合、查找目录、设置键名、mDNS/SSDP 目标串），谁漂了就红。

- **日志**：设置页 →「日志」。每个插件**独立成文件**
  （`~/Library/Application Support/Macast/logs/<LoggerName>.log`，下拉框选），
  不会淹没在 `macast.log` 里；每次启动清空，1 MB × 1 份轮转。
- **镜像起不来，报「ffmpeg 没有列出任何屏幕采集设备（avfoundation）」** ⇒
  要么真没接屏幕，要么**屏幕录制权限没给**（macOS）。给完权限重启 Macast 再试。
  （v0.8 之前这条提示在**有摄像头的机器上也会误报** —— 解析器读不懂 ffmpeg
  的真实输出，见 `AGENTS.md` §4.2 末。）
  macOS 13 及以上正常走 ScreenCaptureKit，这条提示于是只出现在**回落路径**上
  （系统更老、缺绑定，或 SCK 一条帧都没拿到）；但不管走哪条路，缺的都是同一道
  **屏幕录制授权** —— ScreenCaptureKit 也要它。
- **"有声音没画面"**：`grep -aE "video-reconfig|audio-reconfig" ~/Library/Application\ Support/Macast/logs/*.log`
  —— 只有 `audio-reconfig` 说明流里根本没有视频轨（发送端问题）。
- **报「屏幕采集在 3 秒内没有返回画面」**：这一句现在只在**去掉音频口之后仍然拿不到帧**时出现，
  所以它说的是画面那一路（多半是屏幕录制权限），不再是"某处说不清"。给完权限**必须重启 Macast**
  —— 授权只对新启动的进程生效，而 ffmpeg 是我们 spawn 的子进程。反过来，如果镜像起来了、通知里
  带着「本次镜像没有系统声音」，那是**麦克风**那一格（见 §1.5），画面与声音是两道不同的门。
  **macOS 13 及以上先走 ScreenCaptureKit 时是另一种形状**（v0.21）：SCK 的首帧预算是
  **2 秒**（授权被拒时它什么都不产出），超时只记一条
  `ScreenCaptureKit gave no frame (...); retrying with avfoundation` 的 warning，
  然后自动回落去重试一遍 avfoundation，**本次运行不再问 SCK**。所以 13+ 上真采不到帧时，
  通知里最后带的是 avfoundation 那句「3 秒」；那道 2 秒预算问的是同一道授权问题，
  只是提前问出来。SCK 通了、但**系统声音一直没来**是另一种形状（音频 2 秒宽限后
  弃声继续），页面上那句话与 §1.5 同源。
- **装了一个新构建（或新下载）的 `.app` 之后，上面那一条会重新出现一次**：录屏授权记在**那一个包**
  的代码身份上，换了包就要再勾一次。本机 2026-09-23 两次都遇到：替换安装后第一次镜像，带音频与
  只带画面两路都在 3 秒内没有帧；重新在「系统设置 → 隐私与安全性 → 屏幕录制」里勾过之后，
  同一条采集命令立刻出帧（之后 77 秒 3.1 Mbps、丢块 0）。
  **先分清是"没授权"还是"屏幕锁了"**：在同一分钟、同一个设备号从终端跑一次
  `ffmpeg -f avfoundation -i "<屏幕号>:none" -t 3 -c:v libx264 /tmp/probe.mp4` —— 能写出文件
  （本机实测 3 秒 1.1 MB）就说明屏幕没锁、缺的是这个包的授权；写不出来才先去看屏幕状态。
  **屏幕号要先问出来**：`ffmpeg -f avfoundation -list_devices true -i ""`，取
  `AVFoundation video devices:` 下面 `[N] Capture screen 0` 的那个 N。它取决于这台机器上
  还插了什么（摄像头、OBS 虚拟相机、JustStream 的驱动都会占号），本机 2026-10-02 是 **2**，
  2026-09-23 那次是 3 —— 抄一个过期的号，ffmpeg 会报 `Invalid device index` 退出，
  读起来就像"采不到画面"，于是把授权问题判成了链路问题。
  别只看 `TCC.db`：本机实测 `kTCCServiceScreenCapture` 那一行停在 `auth_value=2`、
  `last_modified` 是上一个包的 13:18，而 13:37 装上的新包照样拿不到帧。
  修法是在那一格列表里把 Macast **关掉再打开**（列表里有两个就把旧的删掉、把新的拖进去），
  然后**重启 Macast**。
- **系统声音「装了却没有设备 / 每次点一键设置都要重装」**：先跑 `scripts/selfcheck.py` 看它落在
  §1.5 那张表的哪一格。最常见的是**驱动在磁盘上但音频服务没加载它**（官方 `.pkg` 的 postinstall
  只改权限，从不重启 coreaudiod），**不需要重启电脑**：再点一次一键设置只会要一次管理员密码去重载，
  不会再下载。第二常见的是**麦克风权限**（CoreAudio 看得见、ffmpeg 看不见），
  那条路的终点在「系统设置 → 隐私与安全性 → 麦克风」，装多少个 `.pkg` 都不会改变它。
  **macOS 13 及以上正常走 ScreenCaptureKit 时用不到这一套**：SCK 的音频 tap 不经过
  任何音频设备，BlackHole / 聚合设备 / 麦克风权限都与它无关；而且 SCK 会话弃声之后
  设置页也不会再劝你一键设置 —— 让用户走一遍"装了什么都不会变"的安装器是另一种谎
  （`audio_setup_needed()` 对 SCK 直接答"不需要"）。这一套服务的是**回落路径**
  （系统更老、缺绑定，或 SCK 被拒）。
- **电视找不到这台电脑**：`dns-sd -B _googlecast._tcp` /
  `curl -s 'http://127.0.0.1:58880/api?query=status'`；虚拟机网桥与 Tailscale
  地址会在 `AGENTS.md` §4.1 那一族里出现（只广播承载默认路由的网卡）。
- **本地测试被代理搅局**：`env -u http_proxy -u HTTP_PROXY -u https_proxy -u HTTPS_PROXY <cmd>`。
- **改了设置页前端没反应**：`setting.html` 在启动时缓存，**必须重启应用**。

## 6. 这一族明确不做

FairPlay / 任何 DRM（App 拒绝被镜像就是黑屏，这是设计）· Miracast / Wi-Fi Display
（macOS 没有 P2P API）· AirPlay 镜像的**发送端**（接收端由 §3 补）·
鼠标高亮 · 区域捕获 · 4K 档 · Windows 系统音频 · Cast Streaming 的音频（二期）。
