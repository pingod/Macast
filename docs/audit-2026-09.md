## 三、发现的 Bug 与问题

### 3.1 🐛 BUG: `set_state_duration` 在 `set_observe` 初始化前未收到 duration

**位置**: `macast_renderer/mpv.py:227-237` (`update_state`)
```python
elif res['id'] == ObserveProperty.duration.value:
    if 'data' not in res or res['data'] is None:
        duration = '00:00:00'
    else:
        sec = int(res['data'])
        duration = '%d:%02d:%02d' % ...
        cherrypy.engine.publish('mpv_update_duration', duration)
        ...
    self.set_state_duration(duration)
```
**问题**: `set_state_duration` 调用无论 duration 是否有值都会触发。如果 mpv 在 `--idle` 状态下启动 (无文件), `'data' in res` 但 `res['data'] is None` → `duration = '00:00:00'`, 之后 mpv 加载文件后才会发真正 duration。

**影响**: 启动时 UI/协议状态报告错误的 duration, 持续 1-2 秒直到第一个 observe 事件到达。

**严重性**: 低 (UX, 不影响播放)

**修复建议**:
```python
elif res['id'] == ObserveProperty.duration.value:
    data = res.get('data', None)
    if data is None or data == 0:
        return  # 忽略 idle 状态的初次报告
    sec = int(data)
    duration = '%d:%02d:%02d' % (sec // 3600, (sec % 3600) // 60, sec % 60)
    cherrypy.engine.publish('mpv_update_duration', duration)
    logger.info("update duration " + duration)
    if self.protocol.get_state_transport_state() == 'PLAYING':
        logger.debug("Living media")
    self.set_state_duration(duration)
```

### 3.2 🐛 BUG: `MPVIINA` 插件: `start()` 中 `super(MPVRenderer, self).start()` 调用了错误的 MRO

**位置**: `~/Library/Application Support/Macast/renderer/iina.py:217`
```python
def start(self):
    super(MPVRenderer, self).start()  # ← BUG: 应当是 super(IINARenderer, self)
    ...
```
**问题**: `IINARenderer(MPVRenderer)` 继承自 `MPVRenderer`. `super(MPVRenderer, self)` 跳过了 `MPVRenderer` 直接到 `Renderer` 基类 (实际 MRO 是 `IINARenderer → MPVRenderer → Renderer → object`). 这是 Python 2 风格的 super 调用, 在 Python 3 应为 `super().start()`.

**实际影响**: 因为 `Renderer.start()` 只设置 `self.running = True`, `MPVIINA` 调用 `super(MPVRenderer, self).start()` 等价于 `Renderer.start()` — `self.running` 还是被设置了, 但**跳过了 `MPVRenderer.start()`** 里的 mpv/ipc 线程启动!

但是 IINARenderer 有自己的 `start_iina` 机制, 是由 `set_media_url` 触发的, 不是由 `start()` 触发的, 所以这个 bug 实际不致命。但代码意图混乱。

**严重性**: 低 (潜在隐患, 当前不触发)

**修复建议**:
```python
def start(self):
    super().start()  # IINARenderer → MPVRenderer → Renderer
    logger.info("starting IINARenderer")
    ...
```
或者保留兼容性, 因为 IINARenderer 用了完全不同的启动模型 (`start_iina` 在第一次 `set_media_url` 时才调用), 所以 `start()` 在 IINARenderer 中**根本不需要**调用 super. 实际上 `MPVIINA` 启动时 mpv 进程**不会启动** (除非第一次推送), 这其实是 IINA 的工作方式.

### 3.3 🐛 BUG: `MPVRenderer.reload()` 中 `cherrypy.engine.unsubscribe` 总是被调用, 即使 subscribe 失败

**位置**: `macast_renderer/mpv.py:417-431`
```python
def reload(self):
    ...
    def loadfile():
        ...
        cherrypy.engine.unsubscribe('mpvipc_start', loadfile)

    if self.protocol.get_state_transport_state() == 'PLAYING':
        cherrypy.engine.subscribe('mpvipc_start', loadfile)

    threading.Thread(target=restart, args=()).start()
```
**问题**: `cherrypy.engine.unsubscribe('mpvipc_start', loadfile)` 在 `loadfile` 回调内部调用. 第一次 `mpvipc_start` 触发后回调执行, 取消订阅, 正常. 但如果 mpv 启动失败, `loadfile` 从未被调用, 订阅永远不清理. 第二次 reload 会累积多次订阅。

**严重性**: 低 (边缘场景)

**修复建议**: 使用 `try/finally` 或在 `restart()` 后清理:
```python
def loadfile():
    try:
        ...
    finally:
        try:
            cherrypy.engine.unsubscribe('mpvipc_start', loadfile)
        except Exception:
            pass
```

### 3.4 🐛 BUG: `MPVRenderer.stop()` 中 `os.waitpid(-1, 1)` 不规范

**位置**: `macast_renderer/mpv.py:407`
```python
try:
    os.waitpid(-1, 1)
except Exception as e:
    logger.error(e)
```
**问题**: `os.waitpid(-1, 1)` 是 WNOHANG 模式, 会**回收任意子进程**, 不只是 Macast 的 mpv. 如果用户在 Macast 运行期间启动了其他子进程 (罕见但可能), 会被错误回收。`options=1` 是 WNOHANG, 立即返回 0, 即使没子进程退出。

**严重性**: 低

**修复建议**:
```python
try:
    os.waitpid(self.proc.pid, 0)  # 只等自己
except ChildProcessError:
    pass
except Exception as e:
    logger.error(e)
```

### 3.8 ⚠️ 安全: `cherrypy.config.update` 中 `log.access_file` / `log.error_file` 写入用户配置目录, 无大小限制

**位置**: `macast/server.py:88-90`
```python
cherrypy.config.update({
    'log.screen': False,
    'log.access_file': os.path.join(SETTING_DIR, 'macast.log'),
    'log.error_file': os.path.join(SETTING_DIR, 'macast.log'),
})
```
**问题**: cherrypy 不断往 `macast.log` 追加, 长期运行可能膨胀到 GB. 用户有 SSD 空间压力。

**严重性**: 低-中 (长期使用问题)

**修复建议**:
```python
cherrypy.config.update({
    'log.screen': False,
    'log.access_file': os.path.join(SETTING_DIR, 'macast.log'),
    'log.error_file': os.path.join(SETTING_DIR, 'macast.log'),
    'log.max_size': 10 * 1024 * 1024,  # 10MB
    'log.backup_count': 3,
})
```

### 3.9 ⚠️ 安全: `os.system_shell` / `osascript` 拼接 content 字符串

**位置**: `macast/gui.py:240-246` (`App.dialog`)
```python
res = Setting.system_shell(
    ['osascript', '-e',
     'display dialog "{}" buttons {{"{}","{}"}}'.format(
         content, cancel, ok)
     ])
```
**问题**: 如果 `content` 包含双引号 `",` 会破坏 osascript 语法, 导致命令注入 (虽然只影响自己, 但仍是 bug). 实际 `Setting.system_shell` 没传 `shell=True`, 列表形式安全, 但 `osascript -e` 的字符串参数会被解析, 注入是 AppleScript 层的。

**严重性**: 低-中

**修复建议**: 使用 `osascript` 的 stdin 模式:
```python
res = Setting.system_shell(
    ['osascript', '-e',
     'on run argv\n'
     '  set theText to item 1 of argv\n'
     '  set theCancel to item 2 of argv\n'
     '  set theOK to item 3 of argv\n'
     '  display dialog theText buttons {theCancel, theOK}\n'
     'end run',
     '--', content, cancel, ok]
)
```

### 3.10 ⚠️ 性能: SSDP NOTIFY 每 3 秒, 不限速

**位置**: `macast/server.py:124-131`
```python
self.ssdp_monitor_counter = 0
self.ssdp_monitor = Monitor(cherrypy.engine, self.notify, 3, name="SSDP_NOTIFY_THREAD")
```
**问题**: 3 秒一次 NOTIFY 是 UPnP 规范允许的频率, 但当多个 client 在网络里 search 时, 每次都全网广播. 在大型网络 (公司 / 学校) 会造成 mDNS 拥塞. 但对于家庭网络 OK.

**严重性**: 低

**修复建议**: 保持现状 (UPnP 规范要求 SSDP NOTIFY 间隔 ≤ 30s).

## 四、macast_protocol/ 是否应整合?

### 4.1 上游背景

`pingod/Macast` (我们 fork) **没有** `macast_protocol/` 目录, 只有 `macast/protocol.py` (1066 行的 DLNA 协议实现). 上游 `xfangfang/Macast` 有独立 `macast_protocol/` 目录, 包含若干独立协议插件 (AirPlay, Cast, ...).

### 4.2 仓库实际情况

```bash
$ ls -la /Users/pavia/githome/Macast/
# 没有 macast_protocol/ 目录
$ find . -name "macast_protocol*" 2>/dev/null
# 也没有引用
```

### 4.3 用户目录情况

```bash
$ ls "/Users/pavia/Library/Application Support/Macast/protocol/"
__init__.py
nirvana.py  # 0 字节, 残留
```

`nirvana.py` 是空的占位文件, 2023-08-28 创建后从未填充. 它指向"涅槃协议" — 上游的旧 `macast_protocol/nirvana.py` 插件, 但我们的 fork 没有这个文件.

### 4.4 上游 macast_protocol/ 的存在性

git log 显示 fork 自 6a60737 (2022), 而上游 main 后续添加了 `macast_protocol/`. 我们的 fork 在过去 4 年里已经远超 6a60737, 加上了 Tahoe 修复, CI, mpv 探测等。

### 4.5 决策矩阵

| 选项 | 优点 | 缺点 | 推荐 |
|---|---|---|---|
| A. 不整合 | 保持代码精简; 上游协议插件可能依赖我们没有的依赖; macast/protocol.py 已经够用 | 用户无法用上 AirPlay/Cast 等 | ⭐⭐⭐ 推荐 |
| B. 完整 cherry-pick macast_protocol/ | 完整功能 | 引入大量代码; 上游协议插件未必在 Tahoe 上工作; 维护负担 | ⭐ 不推荐 |
| C. 增量 cherry-pick 单一插件 | 按需引入 | 用户需求不清, 优先级低 | ⭐⭐ 看用户需求 |

### 4.6 **最终建议: 不整合** ✅

理由:
1. 我们的 `macast/protocol.py` (1066 行) 已经是一个**完整的 DLNA/UPnP 协议实现** (`DLNAProtocol(Protocol)`), 这是用户主要使用场景
2. 用户的 `macast_setting.json` `"Macast_Protocol": "DLNA Protocol"`, 表明只用了 DLNA
3. 上游 `macast_protocol/` 包含的 AirPlay / Cast 等协议与 DLNA 是平行协议, 不会增强 DLNA 体验
4. 整合会引入依赖 (`zeroconf`, `pychromecast` 等), 增大 bundle 体积 (当前 101MB → 可能 150MB+)
5. Tahoe 修复已经在 v0.7.2 完成, 上游协议插件在我们的 fork 上不保证能用
6. 如果将来用户需要某个上游协议插件, 再**单独** cherry-pick 那个文件即可

### 4.7 用户行动项

清理掉空的 `nirvana.py`:
```bash
rm "/Users/pavia/Library/Application Support/Macast/protocol/nirvana.py"
```
避免 macast 启动时扫描到这个 0 字节文件 (regex 读 metadata 会失败, 但不会 crash).
